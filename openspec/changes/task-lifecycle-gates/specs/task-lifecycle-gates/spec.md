# Спецификация: task-lifecycle-gates

> Дельта change `task-lifecycle-gates`. Новая capability.

## ADDED Requirements

### Requirement: Этап утверждения плана (PLAN_APPROVED)

Этап `TaskStage.PLAN_APPROVED` вводится в граф между PLANNING и EXECUTION
(порядок enum: PLANNING, PLAN_APPROVED, EXECUTION, VALIDATION, DONE, PAUSED;
сериализация по имени, старые значения читаются как прежде). Ребро
PLANNING→EXECUTION из графа изъято: EXECUTION достижим только через
PLAN_APPROVED (Q3). Гейт двухтактный: переход PLANNING→PLAN_APPROVED
объявляется моделью в ответ на реплику пользователя, утвердившую
представленный план, и ход, в котором он происходит, содержит только
объявление утверждения и вопрос «Приступаю к реализации?» (работы в нём
нет); реализация начинается только в следующем ходе
PLAN_APPROVED→EXECUTION. Переход PLANNING→PLAN_APPROVED делает только
LLM-блок: сервер утверждение не детектирует (G2), фолбэк не
само-утверждается (G3). Мягкость утверждения (FSM не проверяет
утвердительность реплики пользователя) — задокументированный предел (E5).

#### Scenario: Утверждение плана после реплики пользователя

- КОГДА пользователь утвердил представленный план и модель объявила блок
  с переходом PLANNING→PLAN_APPROVED
- ТОГДА переход применяется и этап становится PLAN_APPROVED
- И ответ хода содержит объявление утверждения и вопрос о начале
  реализации, без работы итерации

#### Scenario: Ход PLAN_APPROVED без работы

- КОГДА в ходе происходит переход PLANNING→PLAN_APPROVED
- ТОГДА в тексте ответа этого хода нет выполняемых шагов реализации
- И expected_action фиксирует ожидание подтверждения («Приступаю к
  реализации?»)

#### Scenario: Старт реализации из PLAN_APPROVED

- КОГДА этап PLAN_APPROVED, пользователь подтвердил старт и модель
  объявила блок с переходом PLAN_APPROVED→EXECUTION
- ТОГДА переход применяется и этап становится EXECUTION
- И ответ хода содержит работу итерации реализации

### Requirement: Запрет перескакивания этапов

Таблица рёбер автомата не содержит PLANNING→EXECUTION: предложение
LLM-блока с этим переходом отклоняется (записывается отказ, требование
«Реакция на отклонённый переход»), а зеркало эвристики
(`TaskStateHeuristic.stepToward`) из PLANNING вперёд не уходит вовсе
(арма PLANNING → null). Реализация недостижима без утверждённого плана,
финал (DONE) достижим только через VALIDATION: EXECUTION→DONE нелегален.
Переход в тот же этап легален (обновляются step/expectedAction), всё
прочее — no-op. Жёсткие гарантии (Q3): EXECUTION только через
PLAN_APPROVED, один переход за ход без исключений, фолбэк не
само-утверждается.

#### Scenario: Реализация до утверждения отклонена

- КОГДА этап PLANNING и модель объявила блок с переходом
  PLANNING→EXECUTION
- ТОГДА переход не применяется и этап остаётся PLANNING
- И на сессии записан отказ с описанием отклонённого перехода (E7: отказ
  пишется только для LLM-блоков)

#### Scenario: Финал без валидации отклонён

- КОГДА этап EXECUTION и модель объявила блок с переходом EXECUTION→DONE
- ТОГДА переход не применяется и этап остаётся EXECUTION
- И на сессии записан отказ: в DONE разрешён только из VALIDATION

#### Scenario: Эвристика не перепрыгивает гейт

- КОГДА этап PLANNING, а ответ модели без блока ```task-state``` содержит
  маркеры кода (```, «вот код», «реализация»)
- ТОГДА фолбэк не предлагает переход в EXECUTION (infer → null) и этап не
  меняется
- И отказ не записывается: нелегальное предложение фолбэка — тихий no-op
  (E1, G4)

### Requirement: Реакция на отклонённый переход

Нелегальный переход LLM-блока фиксируется как отказ: человекочитаемая
строка хранится в поле `Session.lastRejectedTransition: String? = null`
(back-compat: legacy-файлы без поля читаются с null; мутаторы
`updateTaskRejection`/`getTaskRejection` в InMemory- и File-сторах; в
Branch-снимки не входит, G7). Отказ пишется только при нелегальном
LLM-блоке и только вне паузы (G4, E3, E7); любые легальные переходы
(LLM-блок или фолбэк) очищают его — отказ живёт ровно до первого такого перехода (E8).
Пока отказ есть, действуют два канала: (1) в блок состояния следующего
хода дописывается строка «ПОСЛЕДНИЙ ПРЕДЛОЖЕННЫЙ ПЕРЕХОД ОТКЛОНЁН: …» с
перечнем разрешённых переходов и инструкцией объяснить пользователю,
почему перескочить нельзя (инъекция эфемерная, в `Session.messages` не
попадает); (2) `ChatResponse` несёт echo `taskRejected` каждым ходом. Фронтенд показывает строку
«Переход отклонён: …» при непустом отказе (Q5). Отказ FSM не смешивается
с несогласием пользователя: реплика без блока — ни переход, ни отказ (E6).

#### Scenario: Запись, инъекция и echo

- КОГДА модель предложила нелегальный переход LLM-блоком вне паузы
- ТОГДА на сессии записан `lastRejectedTransition`, а в ответе хода
  `ChatResponse.taskRejected` не null
- И в блоке состояния следующего хода присутствует строка «ПОСЛЕДНИЙ
  ПРЕДЛОЖЕННЫЙ ПЕРЕХОД ОТКЛОНЁН» с перечнем разрешённых переходов

#### Scenario: Легальный переход очищает отказ

- КОГДА на сессии есть записанный отказ, а следующий ход содержит легальный
  переход (LLM-блоком или через фолбэк)
- ТОГДА переход применяется и `lastRejectedTransition` очищен (null)
- И echo `taskRejected` в `ChatResponse` становится null, строка отказа в
  UI исчезает

#### Scenario: На паузе отказ не пишется

- КОГДА задача на паузе, а ответ прерванного хода содержит нелегальный
  LLM-блок
- ТОГДА переход не применяется (paused-wins) и отказ НЕ записывается
- И записанный ранее отказ переживает паузу и резюме без изменений (E3)

### Requirement: Диалоговый чекпоинт после итерации

Агент ведёт задачу итерациями: за один ответ выполняется ровно одна
итерация текущего этапа, и в конце ответа агент задаёт пользователю вопрос
о продолжении. Если решение следующего шага вариативно, ответ содержит
пронумерованные варианты, и модель ждёт выбора в следующем сообщении
пользователя. Ответ (продолжить / выбрать вариант / остановить) даётся
вводом в поле запроса: кнопок, команд и API утверждения нет (решение #1).
Переход объявляется блоком ```task-state``` только в ответе, следующем за
репликой пользователя, и не более одного перехода за ответ (Q3).

#### Scenario: Вопрос о продолжении в конце итерации

- КОГДА модель завершила одну итерацию текущего этапа
- ТОГДА ответ завершается вопросом о продолжении
- И переход в ответе (если есть) один, объявленный в ответ на реплику
  пользователя

#### Scenario: Пронумерованные варианты при вариативности

- КОГДА следующий шаг задачи решается неоднозначно и модель предлагает
  варианты
- ТОГДА ответ содержит пронумерованный список вариантов
- И модель не объявляет переход, не получив выбор пользователя в
  следующем сообщении

#### Scenario: Один переход за ответ

- КОГДА ответ содержит блок ```task-state```
- ТОГДА за ответ объявлен не более одного перехода
- И переход не объявляется без предшествующей реплики пользователя

### Requirement: Совместимость, пауза и сброс утверждения

`apply()` остаётся Марковским: валидирует только текущий этап, историю
переходов не ведёт (G5). Следствие: старые сессии, записанные до появления
PLAN_APPROVED, в EXECUTION и VALIDATION остаются валидными — миграция
данных не нужна (E4). Утверждение плана переживает паузу/резюм
(PLAN_APPROVED→PAUSED→PLAN_APPROVED) и цикл доработок
VALIDATION→EXECUTION; сбрасывается только переходом DONE→PLANNING (E8):
новая задача начинается с PLANNING без переноса прежнего утверждения.

#### Scenario: Старые сессии без миграции

- КОГДА загружается файл сессии, записанный до появления этапа
  PLAN_APPROVED, с этапом EXECUTION или VALIDATION
- ТОГДА сессия загружается без ошибки, этап остаётся тем же
- И задача продолжает работать на новом графе (EXECUTION→VALIDATION и
  VALIDATION→{EXECUTION, DONE} легальны)

#### Scenario: Пауза из PLAN_APPROVED

- КОГДА пользователь ставит на паузу задачу в этапе PLAN_APPROVED
- ТОГДА этап становится PAUSED с prevStage = PLAN_APPROVED
- И продолжение возвращает задачу в PLAN_APPROVED: утверждение не
  теряется (E8)

#### Scenario: Утверждение переживает цикл валидации

- КОГДА утверждённая задача проходит цикл EXECUTION→VALIDATION→EXECUTION
  (доработка по результатам проверки)
- ТОГДА утверждение плана не теряется и переподтверждение не требуется
- И переход DONE→PLANNING возвращает задачу в PLANNING без переноса
  прежнего утверждения (E8)
