# Изменение: Гейты жизненного цикла задачи

> Статус: draft. Capabilities: task-lifecycle-gates.
> SDD-фиксация гейта утверждения плана; реализация идёт по `tasks.md` этого change.

## Зачем

Управление состоянием задачи в «Штурмане» уже явное (change `task-state-fsm`):
модель объявляет переходы блоками ```task-state```, сервер валидирует их по
таблице рёбер, пауза и продолжение работают на всём графе. Но граф содержит
ребро PLANNING→EXECUTION, а серверный фолбэк (`TaskStateHeuristic`) держит
собственное зеркало этой таблицы и перескакивает из планирования в
реализацию по маркерам кода. Подтверждение пользователя на представленный
план не на пути: реализация начинается до утверждённого плана.

Change ужесточает жизненный цикл задачи: реализация открывается только после
утверждённого пользователем плана (новый этап PLAN_APPROVED, двухтактный
гейт), финал остаётся доступным только после валидации, а нелегальный
переход больше не исчезает молча. Ассистент реагирует видимо: отказ
хранится на сессии, инъектируется в следующий ход (модель объясняет
пользователю, почему перескочить нельзя), и дублируется в UI.

Утверждение плана происходит диалоговым чекпоинтом: после каждой итерации
агент спрашивает пользователя о продолжении, при вариативности предлагает
пронумерованные варианты и ждёт ответ в поле ввода. Кнопок, команд и
API утверждения нет: сервер утверждение не детектирует (G2).

Новых HTTP-роутов нет (G1), механика паузы не меняется (G6).

## Ключевые решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | **Диалоговый чекпоинт**: после каждой итерации агент спрашивает пользователя о продолжении; при вариативности решения предлагает пронумерованные варианты; ответ даётся вводом в поле запроса. Кнопок, команд и API утверждения НЕТ | Подтверждено интервью (21.09): единственный механизм утверждения; заодно исключает серверную лексическую детекцию (G2) и новые роуты (G1) |
| 2 | **Двухтактный гейт**: ход N — PLANNING→PLAN_APPROVED (только объявление утверждения + «Приступаю к реализации?», работы в ответе нет); ход N+1 — PLAN_APPROVED→EXECUTION + работа итерации | Закрытие блокера Q4 (Metis): семантика `apply()` остаётся чистой, действует «один переход за ход» без исключений; утверждение и старт реализованы раздельными ходами |
| 3 | **Изъятие PLANNING→EXECUTION** у LLM-блоков И у серверной эвристики: ребра нет в таблице `TaskStateMachine` и нет в зеркале `stepToward` | Ядро требования: реализация недостижима без утверждённого плана. Без правки зеркала гейт обходился фолбэком (подтверждённая дыра в `TaskStateHeuristic.stepToward`) |
| 4 | **Асимметричное зеркало эвристики**: фолбэк никогда не само-утверждается (PLANNING для него непроходим вперёд); умеет PLAN_APPROVED→EXECUTION по маркерам кода; его нелегальные предложения — тихий no-op без записи отказа | Закрытие блокера Q5 (Metis): без армы PLAN_APPROVED→EXECUTION реальный LLM без блока застрянет после утверждения навсегда; без тихого no-op механика отказа записывала бы сервер-внутренние события, и инъекция лгала бы ассистенту каждый ход (G3, G4, E1) |
| 5 | **Отказ = хранение `lastRejectedTransition` на Session** (человекочитаемая строка, nullable, back-compat дефолт null) + инъекция в блок состояния следующего хода (модель объясняет пользователю) + echo `ChatResponse.taskRejected` каждым ходом, пока есть + строка «Переход отклонён: …» в UI | Видимая реакция на нелегальный переход — второе требование пользователя; три канала (промпт, контракт, UI) дают пользователю и модели полную картину |
| 6 | **Отказ пишется ТОЛЬКО при нелегальном LLM-блоке и ТОЛЬКО вне паузы** (paused-wins остаётся авторитетным) | Metis: отказ — это «модель перескочила», а не «сервер не успел»; на паузе переходы и так не применяются, и запись отказа там была бы ложью |
| 7 | **Отказ очищается ЛЮБЫМ легальным переходом** (LLM-блоком или фолбэком); живёт до него; инъектируется каждый ход, пока есть | Один источник правды о «только что отклонённом»; накапливания и ручной очистки нет; легальный ход делает пометку мёртвой информацией |
| 8 | **Утверждение переживает паузу/резюм (prevStage) и цикл VALIDATION→EXECUTION; сбрасывается только DONE→PLANNING** | Metis: доработка после валидации не отменяет утверждённого плана; новая задача после DONE начинается с нуля — переподтверждать старое не нужно |
| 9 | **Мягкость утверждения — задокументированный предел**: FSM не проверяет, что реплике перехода PLANNING→PLAN_APPROVED предшествовала утвердительная реплика пользователя. Жёсткие гарантии (механические, тестовые): EXECUTION достижим только через PLAN_APPROVED; один переход за ход без исключений; фолбэк не само-утверждается | Метис: утвердительность реплики — вопрос дисциплины модели, не сервера; серверные гарантии ограничены механикой графа, и они полные в пределах этого графа (Q3, E5) |
| 10 | **«Нет, переделай» (реплика пользователя без блока) — не отказ**: перехода нет, запись отказа нет, этап не меняется | Metis: отказ FSM — это «модель предложила нелегальный переход», а не «пользователь не согласен»; разные кодовые пути, отдельный тест (E6) |
| 11 | **`apply()` остаётся Марковским**: валидирует только текущий этап; старые сессии в EXECUTION/VALIDATION, записанные до появления PLAN_APPROVED, валидны без миграции | `apply()` не знает «пути», только текущий этап: старые файлы на диске читаются и работают на новом графе (E4); история переходов не вводится (G5) |

### Граф переходов (полный)

| Переход | Кто инициирует |
|---|---|
| null → PLANNING | LLM-блок или эвристика (создание задачи) |
| PLANNING → PLAN_APPROVED | **только LLM-блок** (эвристика не само-утверждается, G3) |
| PLAN_APPROVED → EXECUTION | LLM-блок или эвристика по маркерам кода |
| EXECUTION → VALIDATION | LLM-блок или эвристика |
| VALIDATION → EXECUTION | LLM-блок или эвристика (доработка) |
| VALIDATION → DONE | LLM-блок или эвристика (после проверки) |
| DONE → PLANNING | LLM-блок или эвристика (новая задача; сбрасывает утверждение) |
| same-stage → same-stage | LLM-блок (обновление step/expectedAction) |
| любой не-PAUSED → PAUSED | пауза-механика (кнопка/команда, без LLM) |
| PAUSED → prevStage | пауза-механика (продолжить, без LLM) |
| всё прочее | no-op; запись отказа только при нелегальном LLM-блоке вне паузы (G4, E3) |

## Edge cases

- **Нелегальное предложение эвристики — тихий no-op.** Фолбэк предлагает
  только легальные ступени или null; если предложение всё же легально
  не проходит `apply()`, переход просто не применяется: без записи отказа,
  без пометки в промпт (E1, G4).
- **Два блока в одном ответе.** Поведение парсера `TaskStateJson` при двух
  fenced-блоках в одном ответе не было проверено; текущее поведение
  закрепляется тестом-пином «как есть», парсер не правится (E2).
- **Пауза при отказе.** Отказ, записанный до паузы, переживает паузу и
  резюме (E8); новый отказ во время паузы НЕ пишется: paused-wins остаётся
  авторитетным, нелегальный блок прерванного хода не применяется и не
  фиксируется (E3, G4).
- **Старые сессии в EXECUTION валидны.** `apply()` Марковский: валидация
  идёт от текущего этапа, и EXECUTION/VALIDATION остаются легальными
  текущими этапами на новом графе — миграции данных нет (E4).
- **LLM объявляет утверждение без утвердительной реплики пользователя.**
  FSM не проверяет утвердительность реплики и пропустит
  PLANNING→PLAN_APPROVED, как только модель объявит его. Известный предел,
  осознанно принятый (решение #9, E5): защита — дисциплина чекпоинта в
  инструкциях, а не механика.

## Ограничения (G/E/Q)

> Номера — стабильные якоря: код и тесты задач 2–8 ссылаются на них из
> change-документов.

### Глобальные (G)

- **G1** Не добавлять новые HTTP-роуты; Triple-список `AuthInterceptTest`
  не меняется.
- **G2** Не добавлять серверную лексическую детекцию утверждения
  (сканеры «да/ок/согласен» запрещены; утверждение — только реплика
  пользователя + блок модели, решение #1).
- **G3** Не давать эвристике возможность предложить PLANNING→PLAN_APPROVED
  (никакого само-утверждения фолбэком).
- **G4** Не записывать отказ для предложений эвристики и на паузе.
- **G5** Не добавлять этапы FSM сверх PLAN_APPROVED; не вводить историю
  переходов/audit-log (автомат остаётся Марковским).
- **G6** Не трогать: парсер/стриппер `TaskStateJson` (кроме теста-пина),
  механику паузы/продолжения и их роуты, `/api/cancel`, judge/facts/
  invariants machinery, `AgentLoop.kt`, `SessionHistory`.
- **G7** Не захватывать `lastRejectedTransition` в Branch-снимки (общее на
  сессию, зеркало taskState).
- **G8** Не добавлять конфиг-швы: гейт always-on.

### Краевые (E)

- **E1** Нелегальное предложение эвристики — тихий no-op: переход не
  применяется, отказ не записывается, инъекция не меняется.
- **E2** Два блока ```task-state``` в одном ответе: текущее поведение
  парсера закрепляется тестом-пином; парсер не правится.
- **E3** Пауза при отказе: записанный отказ сохраняется (переживает
  паузу/резюм), новые отказы на паузе не пишутся.
- **E4** Старые сессии в EXECUTION/VALIDATION читаются и работают без
  миграции (Марковская валидация от текущего этапа).
- **E5** LLM объявляет PLANNING→PLAN_APPROVED без утвердительной реплики
  пользователя: FSM пропустит (задокументированный предел, решение #9).
- **E6** «Нет, переделай» — реплика без блока: перехода нет, отказа нет,
  этап не меняется (отдельный тест, решение #10).
- **E7** Записи отказа нет при создании задачи (null → первый этап) и при
  same-stage обновлениях.
- **E8** Утверждение и отказ переживают паузу/резюм и цикл
  VALIDATION→EXECUTION; утверждение сбрасывается только DONE→PLANNING;
  отказ — любым легальным переходом.

### Качество (Q)

- **Q1** Тесты без сети (FakeLLMClient / mock-llm.py); существующие 515+
  тестов не ломаются.
- **Q2** Фронтенд: цвета только из tokens.css (`:root`), без
  `as any`/`@ts-ignore`, без console.log, без новых npm-зависимостей.
- **Q3** Жёсткие гарантии (механические, покрыты тестами): EXECUTION
  недостижим без PLAN_APPROVED; один переход за ход без исключений;
  фолбэк не само-утверждается.
- **Q4** Существующие режимы mock-llm не ломаются; новые режимы
  plan-approve / start-execution / jump-approval / checkpoint расширяют
  TASK_MODES, скрипт остаётся stdlib-only.
- **Q5** Echo taskState (существующий) сохраняется; StatusLine получает
  метки всех 6 этапов, включая «План утверждён».

## Что меняется (сводка)

- `TaskStage.kt`: новое значение `PLAN_APPROVED` в enum (между PLANNING и
  EXECUTION; сериализация по имени, старые JSON читаются как прежде).
- `TaskStateMachine.kt`: ребро PLANNING→EXECUTION заменено на
  PLANNING→PLAN_APPROVED, добавлено PLAN_APPROVED→EXECUTION; обновлён
  KDoc-контракт графа и гейта.
- `TaskStateHeuristic.kt`: асимметричное зеркало в `stepToward` (PLANNING
  → null для вперёд, арма PLAN_APPROVED→EXECUTION) + KDoc асимметричного
  правила.
- `SessionStore.kt` / `FileSessionStore.kt`: поле
  `Session.lastRejectedTransition: String? = null` (KDoc back-compat) +
  `updateTaskRejection`/`getTaskRejection` в интерфейсе и обеих
  реализациях; `Entry`/`snapshot()` зеркалят поле.
- `Models.kt` + `frontend/src/api/types.ts`: `ChatResponse.taskRejected:
  String?` / `taskRejected?: string | null` — синхронно в одной задаче.
- `TaskStatePrompts.kt`: чекпоинт-дисциплина в блоке состояния (одна
  итерация за ответ, вопрос о продолжении, варианты, два такта гейта,
  список разрешённых переходов) + строка «ПОСЛЕДНИЙ ПРЕДЛОЖЕННЫЙ ПЕРЕХОД
  ОТКЛОНЁН» при непустом отказе.
- `Routes.kt` (`finalizeResponse`): запись отказа (только нелегальный
  LLM-блок вне паузы), очистка любым легальным переходом, echo
  `taskRejected` после мутаций; `handleAgent` — существующая точка
  инъекции, новые слоты не добавляются.
- Фронтенд: `useChatStream.ts` (приём `taskRejected` в
  `applyChatResponse`), `stores/session.ts` (`setTaskRejected`),
  `StatusLine.tsx` (+ CSS module): бейдж «План утверждён» и строка
  «Переход отклонён: …» при непустом отказе.
- `scripts/mock-llm.py`: режимы plan-approve / start-execution /
  jump-approval / checkpoint; `/control` расширен.
- OpenSpec: этот change (сам документ); код и тесты идут по `tasks.md`.

- Само-утверждение эвристикой, эвристическое распознавание «да/ок/
  согласен» (G3).
- Этапы FSM сверх PLAN_APPROVED; история переходов/audit-log (G5).
- Branch-снимки `lastRejectedTransition` (G7).
- Конфиг-швы: гейт always-on (G8).
- Правка `TaskStateJson` (кроме теста-пина), механики паузы, `/api/cancel`,
  judge/facts/invariants, `AgentLoop.kt`, `SessionHistory` (G6).
- Коммиты (конвенция репозитория: рабочее дерево остаётся
  незафиксированным).
- Архивирование других OpenSpec changes, правка других specs.
