# Спецификация: Изоляция данных пользователей

## ADDED Requirements

### Requirement: Изоляция сессий

Сессия MUST иметь поле `userId: String?`. Список, удаление и чистка
сессий доступны только в границах текущего пользователя:
`GET /api/sessions` отдаёт только сессии владельца, операции по
`/api/session/{id}` для чужой сессии → 404. Файлы сессий без `userId`
(legacy) читаются с `userId == null` без ошибок.

#### Scenario: Два пользователя не видят сессий друг друга
- **WHEN** пользователь A имеет 2 сессии, пользователь B запрашивает
  `GET /api/sessions`
- **THEN** B видит только свои сессии; сессии A отсутствуют

#### Scenario: Чужая сессия по id
- **WHEN** пользователь B делает `GET /api/session/{id_A}` или
  `DELETE /api/session/{id_A}`
- **THEN** 404, без раскрывающих деталей

#### Scenario: Legacy-сессия читается
- **WHEN** в `dataDir/sessions/` лежит файл без поля `userId`
- **THEN** сессия видна в общем перечислении с `userId == null`, исключений нет

### Requirement: Изоляция долговременной памяти

Долговременная память MUST храниться per-user:
`dataDir/memory/{userId}/longterm.json`. Все роуты `/api/memory*`
включая `/api/memory/overview` резолвят userId из токена и работают со
стором этого пользователя. Форматы записей, капы и таксономия
memory-kind (включая `kind: profile`) не меняются.

#### Scenario: Записи не пересекаются
- **WHEN** пользователь A сохранил запись, пользователь B делает
  `GET /api/memory`
- **THEN** список B пуст; `GET /api/memory/{id_A}` под B → 404

#### Scenario: Чужая запись по id
- **WHEN** пользователь B делает `PUT` или `DELETE /api/memory/{id_A}`
- **THEN** 404, без деталей о существовании записи

### Requirement: Изоляция рабочей памяти и предпочтений

Рабочая память завязана на сессии, а сессии per-user, поэтому рабочая
память наследует изоляцию сессий: файлы `dataDir/working/` чужих сессий
недоступны. Файлы `dataDir/preferences/{userId}.json` MUST доступны
только владельцу через `GET/PUT /api/preferences` своего токена.

#### Scenario: Чужая рабочая память недоступна
- **WHEN** пользователь B запрашивает рабочую память сессии A
  (`GET /api/session/{id_A}/working`)
- **THEN** 404 (сессия чужая)

#### Scenario: Чужие предпочтения недоступны
- **WHEN** пользователь B шлёт запрос, который мог бы прочитать
  предпочтения A
- **THEN** B получает только свои предпочтения; API предпочтений других
  пользователей не существует

### Requirement: Журнал запросов per-user

Записи журнала (`ExchangeLog`) MUST помечаться `userId` отправителя.
`GET /api/log` MUST возвращать только записи текущего пользователя.

#### Scenario: Журнал не утекает
- **WHEN** пользователь A и B обменялись сообщениями, B запрашивает
  `GET /api/log`
- **THEN** в ответе только записи B; записи A отсутствуют

### Requirement: Кросс-доступ = 404, а не 403

Система MUST NOT раскрывать существование чужих ресурсов: любой доступ
к ресурсу другого пользователя (сессия, запись памяти) отвечает 404.

#### Scenario: Единственный код ответа на чужое
- **WHEN** запрашивается чужая сессия, чужая запись памяти, чужой
  working-файл
- **THEN** во всех случаях 404, никогда 403

### Requirement: Предпочтения и «Топливо»: два разных механизма

Поле «Длина ответов» реализуется ТЕКСТОВОЙ инструкцией в блоке
предпочтений (бэкенд не управляет generation-параметрами модели).
Слайдер «Топливо» остаётся жёстким капом токенов запроса и имеет
приоритет над рекомендацией по длине. Тесты MUST NOT ассертить
токен-каунты по длине.

#### Scenario: Инструкция в промпте
- **WHEN** `length = «развернуто»`
- **THEN** блок предпочтений содержит строку о длине с ориентиром
  ≈ 10 тыс. токенов; запрос к LLM не получает никакого параметра
  `max_tokens` от предпочтений

#### Scenario: Кап «Топливо» главнее
- **WHEN** «Топливо» выставлено ниже ориентира выбранной длины
- **THEN** запрос обрезается капом «Топливо», длина из предпочтений не
  расширяет лимит

### Requirement: Глобальная эвикция и общая песочница (задокументировано)

Эвикция `MAX_SESSIONS=50` остаётся ГЛОБАЛЬНОЙ для всех пользователей:
при переполнении удаляется самая старая сессия вне зависимости от
владельца; per-user квоты вне рамок. `GET /api/files/{name}` остаётся
ОБЩЕЙ файловой песочницей: защищена токеном, но содержимое общее для
всех пользователей. Оба решения MUST быть задокументированы.

#### Scenario: Переполнение лимита сессий
- **WHEN** суммарно создано более 50 сессий у разных пользователей
- **THEN** самая старая (по любой принадлежности) эвиктируется; ошибок
  нет

#### Scenario: Файловая песочница общая
- **WHEN** пользователь B читает файл, созданный пользователем A через
  песочницу
- **THEN** файл доступен (общая песочница, защищена только токеном)
