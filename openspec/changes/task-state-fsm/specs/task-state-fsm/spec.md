# Спецификация: task-state-fsm

> Дельта change `task-state-fsm`. Новая capability.

## ADDED Requirements

### Requirement: Хранение состояния задачи на сессии

Состояние задачи — объект `TaskState` (stage, step, expectedAction,
prevStage?) — хранится в отдельном поле `Session.taskState: TaskState? = null`,
а не как сообщение внутри `Session.messages`. Поле живёт и умирает вместе с сессией, как facts и summary. Default обязателен:
старые файлы сессий без этого поля загружаются с taskState=null. Операции
хранилища `updateTaskState(sessionId, state)` и `getTaskState(sessionId)`
реализованы в InMemory- и File-сторах. Снимки веток (Branch) taskState не
содержат: состояние — общее на сессию (осознанное ограничение).

#### Scenario: Старый файл сессии без поля taskState

- КОГДА загружается JSON сессии, записанный до появления поля
- ТОГДА сессия загружается без ошибки
- И taskState == null

#### Scenario: Round-trip состояния через стор

- КОГДА состояние записано через `updateTaskState` и прочитано через
  `getTaskState` (InMemory или FileSessionStore)
- ТОГДА прочитанное состояние совпадает с записанным
- И снапшот сессии содержит состояние

#### Scenario: Ветка не захватывает состояние

- КОГДА в сессии с непустым taskState создаётся снимок ветки (Branch)
- ТОГДА снимок ветки не содержит taskState
- И состояние остаётся общим на сессию

### Requirement: Валидация переходов автоматом

Переходы состояния задаёт гибридный драйвер: LLM выводит в финальном ответе
fenced-блок ```task-state {"stage":…,"step":…,"expected_action":…}``, сервер
парсит его и применяет переход только если он легален по таблице рёбер:
null→planning; planning→execution; execution→validation; validation→execution;
validation→done; done→planning; любой не-paused этап (включая done)→paused
(запомнить prevStage); paused→prevStage; переход «в тот же этап» легален
(обновляются step/expectedAction). Всё прочее — no-op: состояние не меняется
и не фиксируется как сбой. Парсится только финальный ответ (не
промежуточные итерации AgentLoop). Несколько блоков в одном ответе → выигрывает
последний. Блок отсутствует, JSON битый или stage не входит в enum → null →
no-op. Капы длин: step ≤ 120 символов, expected_action ≤ 200 символов
(обрезка на входе в автомат).

#### Scenario: Легальная цепочка переходов

- КОГДА модель по ходу хода объявляет переходы null→planning,
  planning→execution, execution→validation, validation→done
- ТОГДА каждый переход применяется и состояние движется по графу
- И step/expectedAction обновляются из блоков модели

#### Scenario: Нелегальный переход — no-op

- КОГДА модель объявляет переход done→execution (или planning→done,
  null→execution)
- ТОГДА состояние не меняется (этап остаётся прежним)
- И ответ возвращается как обычно, без фиксации сбоя

#### Scenario: Несколько блоков — выигрывает последний

- КОГДА ответ содержит два fenced-блока ```task-state``` с разными stage
- ТОГДА парсинг берёт значение из последнего блока (при легальности перехода
  от текущего состояния)
- И стрип удаляет оба блока из текста ответа

#### Scenario: Сбой парсинга — no-op

- КОГДА в ответе нет блока, JSON внутри блока битый или stage содержит
  значение вне enum
- ТОГДА состояние не меняется
- И ответ возвращается как обычно (200, чат не ломается)

### Requirement: Инъекция состояния в промпт

Каждый ход агентного режима сервер подставляет в промпт (seed `handleAgent`)
эфемерную system-строку с состоянием задачи: этап, текущий шаг, ожидаемое
действие — по образцу инъекции preferences/memory. Строка не пишется в
`Session.messages` и не режется `SessionHistory.trim`. Варианты: обычный
(этап + шаг + ожидаемое действие и правило «в финальном ответе объяви
переход блоком ```task-state```»), paused («Задача на паузе. Не объявляй
переходы; отвечай на уточняющие вопросы.»), null («Задача не начата —
приступая, объяви planning»).

#### Scenario: Блок состояния в исходящем запросе

- КОГДА сессия имеет состояние (stage=execution, непустой step) и
  пользователь отправляет сообщение
- ТОГДА запрос к модели содержит system-строку с этапом, шагом и
  ожидаемым действием
- И после хода строка не присутствует в истории сессии

#### Scenario: Paused-вариант блока

- КОГДА задача на паузе (stage=paused) и пользователь отправляет сообщение
- ТОГДА system-строка содержит «Задача на паузе» и запрет объявлять
  переходы
- И состояние не меняется (авто-resume по обычному сообщению не
  происходит)

#### Scenario: Состояние не начато

- КОГДА сессия не имеет состояния (taskState == null)
- ТОГДА system-строка — вариант «Задача не начата» с инструкцией объявить
  planning при старте
- И после первого легального перехода состояние появляется в сессии

### Requirement: Пауза и продолжение (кнопка + команды)

Пауза и продолжение — прямое действие пользователя без вызова LLM: кнопка UI
(POST `/api/task/pause` и POST `/api/task/resume`, body `{sessionId}`, ответ
`{taskState}`, 404 на неизвестную сессию) и ровно 4 команды в чате:
«пауза», «/пауза», «продолжить», «/продолжить» — точное совпадение после
trim+lowercase, обрабатываются до LLM-вызова с системным ответом. Оба роута
защищены. Пауза переводит любой не-paused этап в PAUSED (запомнив prevStage);
продолжение — обратный переход в prevStage, step/expectedAction
сохраняются. Операции идемпотентны. Пауза в полёте (до финализации ответа)
побеждает LLM-переход: переход применяется только после свежего
перечитывания store, и если текущий этап PAUSED — no-op. Пауза при отсутствии
активной задачи (null) — no-op: системное сообщение «Нет активной задачи»,
API отвечает `{taskState: null}`.

#### Scenario: Команда «пауза» без вызова LLM

- КОГДА пользователь отправляет сообщение «пауза» (или «/пауза») при
  активной задаче
- ТОГДА возвращается системный ответ («Задача поставлена на паузу. Этап: …»)
  без вызова LLM
- И состояние становится paused с prevStage = предыдущий этап

#### Scenario: «Сделай паузу» — не команда

- КОГДА пользователь отправляет сообщение «сделай паузу»
- ТОГДА сообщение уходит в LLM (обычный путь)
- И перехват состояния не происходит

#### Scenario: Пауза в полёте побеждает LLM-переход

- КОГДА запрос паузы (кнопкой или командой) поступает до финализации хода, а
  ответ хода содержит легальный переход
- ТОГДА свежее перечитывание store показывает stage=paused
- И LLM-переход не применяется (no-op)

#### Scenario: Пауза при отсутствии активной задачи

- КОГДА пользователь ставит на паузу сессию с taskState == null
- ТОГДА no-op: системный ответ «Нет активной задачи»
- И API отвечает `{taskState: null}`

#### Scenario: Продолжение после паузы

- КОГДА пользователь продолжает задачу на паузе (кнопкой или командой
  «продолжить»/«/продолжить»)
- ТОГДА этап возвращается в prevStage
- И step/expectedAction сохранены как до паузы

#### Scenario: Незнакомая сессия

- КОГДА POST `/api/task/pause` вызван с неизвестным sessionId
- ТОГДА ответ 404
- И состояния других сессий не затрагиваются

### Requirement: Видимость состояния во фронтенде

Контракт `ChatResponse` содержит поле `taskState` (nullable, зеркало
Kotlin-типа `TaskState`: stage/step/expectedAction/prevStage) — echo
состояния каждым ходом вместе с ответом. Фронтенд принимает `taskState` в
`applyChatResponse` (каждый ход, безусловно, по образцу `data.facts` →
`setFacts`) и отображает: `StatusLine` показывает бейдж этапа (Планирование /
Исполнение / Проверка / Готово / Пауза) и строку «Шаг: <step> · Далее:
<expectedAction>»; при taskState == null зона индикатора пуста. В зоне SendBar
— кнопка Пауза↔Продолжить по образцу кнопки «Стоп»: label «Пауза» при
активной задаче (stage != paused и != null), «Продолжить» при paused,
disabled при taskState == null; клик вызывает соответствующий POST-роут через
`api/client.ts`, состояние обновляется из ответа. При рендере записей
Бортового журнала блоки ```task-state``` вырезаются (defense-in-depth;
сервер уже стирает их до истории).

#### Scenario: Echo состояния каждым ходом

- КОГДА пользователь отправляет сообщение и сервер возвращает ответ
- ТОГДА ChatResponse содержит актуальный taskState (echo после возможного
  обновления)
- И фронтенд получает его без отдельного запроса

#### Scenario: Индикатор и кнопка при активной задаче

- КОГДА задача активна (stage=execution, непустой step)
- ТОГДА в StatusLine виден бейдж «Исполнение» и строка с шагом и
  ожидаемым действием
- И label кнопки «Пауза», кнопка не disabled

#### Scenario: Задачи нет

- КОГДА taskState == null
- ТОГДА зона индикатора пуста (бейджа нет)
- И кнопка паузы disabled

#### Scenario: Журнал не показывает протокольный блок

- КОГДА в тексте ответа записи журнала присутствует блок ```task-state```
- ТОГДА запись журнала отображает текст без этого блока
- И остальной текст сохранён дословно
