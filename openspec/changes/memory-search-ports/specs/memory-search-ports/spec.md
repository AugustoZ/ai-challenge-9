# Спецификация: Порты поиска и хранения памяти (memory-search-ports)

## ADDED Requirements

### Requirement: Доступ к долговременной памяти через порт MemoryRepository

Весь код вне пакета `com.example.aiweb.memory` (инструменты агента, HTTP-роуты,
инъекция контекста) MUST работать только с интерфейсом `MemoryRepository`,
не зная о конкретном хранилище. Текущая файловая реализация
(`LongTermMemoryStore`) MUST стать реализацией этого интерфейса без изменения
своего публичного поведения.

#### Scenario: Потребители памяти не зависят от хранилища
- **WHEN** инструменты агента и роуты обращаются к долговременной памяти
- **THEN** они используют только методы `MemoryRepository`; замена реализации
  не требует правок потребителей

### Requirement: Поиск по памяти через порт MemorySearchEngine с выбором из конфига

Релевантный поиск MUST выполняться через интерфейс `MemorySearchEngine`.
Реализация выбирается из конфига (`memory.search`): null или "keyword" —
текущий keyword-скоринг (`KeywordMemorySearch`, логика 1:1 из `MemoryRetriever`);
любое другое значение — ошибка старта приложения с русским текстом и
перечислением доступных значений.

#### Scenario: Дефолтный конфиг — прежнее поведение
- **WHEN** конфиг не содержит раздел memory (или search = "keyword") и
  пользователь отправляет запрос при непустой памяти
- **THEN** блок памяти строится как раньше: профили всегда + топ релевантных
  записей по keyword-скорингу

#### Scenario: Неизвестная стратегия поиска
- **WHEN** конфиг содержит `memory.search = "fts"` (реализация ещё не добавлена)
- **THEN** приложение не стартует; текст ошибки на русском, называет значение
  и доступные варианты ("keyword")

### Requirement: MemoryRetriever — оркестратор без собственной поисковой логики

`MemoryRetriever` MUST получать профили из `MemoryRepository`, релевантные
записи — из `MemorySearchEngine`, и отвечать только за бюджеты и формат блока.
Результат на текущих данных MUST быть идентичен прежнему (те же строки, порядок
и бюджеты 1800/2400 символов).

#### Scenario: Блок памяти не изменился
- **WHEN** в памяти есть профили, решения/знания и рабочие заметки, запрос
  содержит ключевые слова
- **THEN** блок памяти совпадает с прежним (профили всегда, топ-6 по score>0,
  ties по updatedAt, обрезка по бюджетам)

### Requirement: Контрактный тест-набор репозитория

Обязательные поведения репозитория MUST быть зафиксированы абстрактным
набором тестов (`MemoryRepositoryContractTest`): CRUD, counts по видам,
фильтры kind/q, капы, персист roundtrip. Реализация `LongTermMemoryStore`
MUST проходить набор; будущие реализации обязаны проходить его же без правок.

#### Scenario: Текущая реализация проходит контракт
- **WHEN** запускается набор контрактных тестов для файловой реализации
- **THEN** все тесты зелёные; набор переиспользуется будущими бэкендами как есть

### Requirement: Конфиг-швы с обратной совместимостью

Новые поля конфига (`memory.search`, `memory.embedding`) MUST быть nullable
с дефолтами: старый config.json обязан работать без изменений (доктрина
проекта). Раздел embedding принимается конфигом, но не активирует никакую
реализацию в этом чейндже.

#### Scenario: Старый конфиг без раздела memory
- **WHEN** config.json не содержит "memory"
- **THEN** приложение стартует, память работает в режиме keyword как раньше

### Requirement: Нерегрессия

Рефакторинг MUST NOT менять: формат блока памяти, капы, HTTP API памяти,
инструменты агента, дисциплину промта, учёт токенов. Все существующие тесты
(330 бэкенд / 207 фронт) проходят; E2E-сценарий «запомни» на мок-стенде
работает как раньше.

#### Scenario: E2E-смоук после рефакторинга
- **WHEN** на мок-стенде выполняется сценарий «запомни: …» и фильтр
  `/api/memory?q=`
- **THEN** поведение идентично прежнему: запись сохранена с source=agent,
  поиск фильтрует, ответ API не изменился
