# Изменение: PR-review pipeline — автоматическое AI-ревью кода

> Статус: draft. Capabilities: pr-review-pipeline.
> Предпосылка: MCP-платформа Штурмана (change `mcp-integration`) уже в проде;
> сервер `github` подключён (`config.json`, `ghcr.io/github/github-mcp-server`,
> toolsets: repos/issues/pull_requests). Этот change строит на нём пайплайн
> ревью PR.

## Задание

Настрой пайплайн, в котором бот Штурман анализирует новый PR:
получает diff и изменённые файлы → использует RAG (документация + код) →
выдаёт текст ревью: потенциальные баги, архитектурные проблемы, рекомендации.
Минимальный результат: пайплайн (например GitHub Action) запускается на PR,
ассистент получает diff, возвращает ревью. Результат: автоматическое
AI-ревью кода.

## Зачем

Ревью PR сейчас делается вручную. У Штурмана уже есть всё необходимое:
агентный цикл + инструменты, MCP-сервер GitHub (diff, файлы, комментарии),
RAG-поиск по базе знаний (внешний индексер: документация + код), детерминированные
пайплайн-сценарии (`config/pipelines/*.json` с плейсхолдерами
`${steps.N.result}`). Не хватает склейки: сценария ревью, моста «GitHub
Action → локальный бот» и тулов RAG в пайплайне.

## Топология: GitHub Action ↔ локальный бот

Штурман живёт на Mac пользователя (LLM — LM Studio/Bionic локально), GitHub
Actions — в облаке. Прямой доступ облака к `localhost:8080` невозможен.
Варианты:

| Вариант | Суть | Плюсы | Минусы | Решение |
|---|---|---|---|---|
| **A. Self-hosted runner** | GitHub Action `on: pull_request` выполняется runner'ом на Mac и дергает `http://localhost:8080/api/pipeline/run` | Без туннелей и внешней экспозиции; секреты не покидают машину; локальная LLM доступна | Runner должен быть запущен; review-комментарий постится через GitHub MCP (PAT уже в конфиге) | **Выбран** |
| B. Туннель (cloudflared/ngrok) | Cloud Action POST'ит через публичный URL | Обычный runner | Публичная экспозиция API; туннель — лишний сервис и точка отказа; нужен отдельный CI-токен | Отложено |
| C. Локальный поллер | Бот по расписанию сам опрашивает открытые PR через GitHub MCP | Zero-инфраструктура | Не GitHub Action; латентность = интервал опроса; триггер не на PR-событие | Запасной (fallback, если runner неудобен) |

Выбор A: минимальная новая поверхность, секреты остаются локальными,
«пайплайн запускается на PR» выполняется буквально.

## Ключевые решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | **Сценарий `config/pipelines/pr-review.json`** на существующем PipelineService (детерминированные шаги + плейсхолдеры), а не LLM-оркестрация | Конвенция change mcp-integration (решение 5); ревью воспроизводимо, шаги наблюдаемы через `GET /api/pipeline/status` |
| 2 | **Источник данных — GitHub MCP-тулы**: `mcp__github__get_pull_request_diff` + `mcp__github__get_pull_request_files` | Diff и список файлов уже доступны подключённым сервером; кап 20 000 симв. адаптера — естественный бюджет |
| 3 | **Новый нативный пайплайн-тул `rag_search`** (в `pipelineExtraTools`, обёртка над `RagService`) | RAG-блок инжектится только в чат-сценарий (`handleAgent`); пайплайну нужен прямой поиск. Имена изменённых файлов + заголовок PR = запрос; кап вывода как у других тулов |
| 4 | **Ревью генерирует `summarize`** (LLM-тул) с жёсткой инструкцией формата: «Баги / Архитектурные проблемы / Рекомендации», язык — русский | Утилита уже есть; структура ревью фиксируется инструкцией, не кодом |
| 5 | **Публикация ревью — `mcp__github__create_and_submit_pull_request_review`** (event=COMMENT) | Ревью видно в UI GitHub как review; нужен тот же PAT, что уже в `config.json` |
| 6 | **Мост — self-hosted runner + тонкий workflow**: Action получает `pr.number`/`repo`, делает `curl -X POST /api/pipeline/run` с телом сценария-параметрами, ждёт `GET /api/pipeline/status` | Решение A; workflow ≤ 50 строк; токен Штурмана не хранится в GitHub |
| 7 | **Параметры PR передаются в сценарий как аргументы запуска** (`POST /api/pipeline/run` с overrides: `repo`, `prNumber`), а не зашиты в JSON | Один сценарий обслуживает любой PR; сценарий остаётся детерминированным |
| 8 | **Дедупликация**: пометка «отревьюено» в `<dataDir>/pipeline/pr-review/{repo}#{pr}.json`; повторный запуск того же commit → 409/`skipped` | Пересинхронизация ветки порождает повторные `pull_request` события; повторное ревью — спам |
| 9 | **Секреты — только `config.json`**; workflow не получает токен Штурмана, GitHub PAT в боте | Guardrail проекта; runner локальный, утечка в логи Action исключена (API-ответы не логируются с телами) |
| 10 | **Капы**: diff > 20 000 симв. режется адаптером; при обрезке в ревью явно помечается «проанализирована часть diff» | Большие PR не должны молча деградировать качество; фиксируется в результате шага |

## Поток данных (Wave 2, целевой вид)

```
PR opened/synchronize
  → GitHub Action (self-hosted runner на Mac)
    → POST /api/pipeline/run {scenario: pr-review, params: {repo, pr}}
      → s1 get_pull_request_diff     (mcp__github)
      → s2 get_pull_request_files    (mcp__github)
      → s3 rag_search {query: title+files}   (новый тул, RagService)
      → s4 summarize {diff+files+rag, instruction: формат ревью}
      → s5 create_and_submit_pull_request_review {body: s4}  (mcp__github)
    → GET /api/pipeline/status до terminal-статуса
    → summary в выводе Action
```

## Edge cases

- **Diff не влезает в 20 000 симв.** (большие PR): шаг s1 вернёт усечённый
  текст; в ревью обязательная пометка об усечении. Опционально (Wave 3) —
  пофайловый обход через `get_pull_request_files` + выборочный diff.
- **PR из форка** (`pull_request_target` vs `pull_request`): код чужого PR
  НИКОГДА не исполняется — только читается; Action на `pull_request` имеет
  read-only токен, публикация идёт из бота через PAT.
- **RAG-сайдкар недоступен**: `rag_search` fail-open (пустой блок), ревью
  продолжает строиться по diff — по образцу `runJudge`/RAG v1.
- **GitHub MCP недоступен** (нет Docker/сети): шаг падает, пайплайн =
  failed, Action краснеет с текстом ошибки из статуса.
- **Повторное событие на тот же commit**: дедупликация (решение 8) —
  `skipped`, без повторного комментария.
- **Бот не поднят в момент срабатывания Action**: curl падает на
  connection refused, Action краснеет с внятным сообщением
  «Штурман не запущен».
- **Одновременные запуски** (несколько PR подряд): ограничение
  PipelineService «1 активный запуск» → второй Action получает 409 и
  ретраит с бэкоффом (в workflow, до 3 попыток).

## Волны

1. **Волна 1 — ручной ревью по команде** (без Action): тул `rag_search`,
   сценарий `pr-review.json`, параметры запуска (repo/pr) в
   `POST /api/pipeline/run`, дедупликация. Проверка: запуск по реальному
   открытому PR руками, ревью появляется в GitHub.
2. **Волна 2 — мост GitHub Action**: self-hosted runner на Mac,
   `.github/workflows/pr-review.yml` (триггер `pull_request`, curl на
   localhost, poll статуса, 409-ретраи). Проверка: открытый PR получает
   ревью без ручных действий.
3. **Волна 3 — качество и гигиена** (опционально): пофайловая стратегия
   для больших diff; выборочная ревью только помеченных PR (лейбл
   `ai-review`); отчёт `reports/pr-review-samples.md` с примерами ревью
   и правками промта инструкции.

## Границы (не делаем)

- Не храним токен Штурмана в GitHub Secrets и не делаем постоянный
  CI-токен в TokenManager (guardrail: токены в памяти, рестарт = re-login).
- Не исполняем код из PR ни в песочнице, ни в тестах.
- Не пишем коммиты/строки в файлах PR — только review-комментарии
  (event=COMMENT, без `REQUEST_CHANGES`, пока не подтверждено качество).
