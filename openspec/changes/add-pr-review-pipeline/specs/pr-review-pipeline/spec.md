# Спецификация: pr-review-pipeline

> Delta поверх capabilities `mcp-integration` (PipelineService, MCP-клиент)
> и `add-rag-mode` (RagService). Формат: ADDED-требования.

## ADDED Requirements

### Requirement: Тул rag_search для пайплайнов

Система ДОЛЖНА предоставлять нативный тул `rag_search`, доступный только в
пайплайнах (через `pipelineExtraTools`, без изменения основного реестра
`GET /api/tools`).

- Аргументы: `query` (строка, обязательный), `k` (число, опционально,
  дефолт — из RagConfig).
- Вывод: текст найденных документов (метаданные + snippet) с капом
  20 000 символов.
- Fail-open: недоступность RAG-сайдкара — ok=true с текстом
  «RAG недоступен»; падение пайплайна из-за RAG запрещено.

#### Scenario: поиск по базе
- **WHEN** пайплайн вызывает `rag_search` с `query` при живом сайдкаре
- **THEN** тул возвращает ok=true и текст найденных документов

#### Scenario: сайдкар недоступен
- **WHEN** RAG-сайдкар сбит или таймаут
- **THEN** тул возвращает ok=true с текстом «RAG недоступен» (fail-open)

### Requirement: Параметры запуска пайплайна

`POST /api/pipeline/run` ДОЛЖЕН принимать параметры запуска (карту
`params`), подставляемые в плейсхолдеры аргументов шагов сценария.

- Плейсхолдер вида `${params.name}` в аргументах шага заменяется
  значением параметра.
- `pr` ДОЛЖЕН валидироваться как число; неизвестные параметры — ошибка
  запуска (400), а не молчаливая подстановка пустой строки.

#### Scenario: подстановка параметров
- **WHEN** запускается сценарий с шагом, чей аргумент содержит
  `${params.pr}`, и в запросе `params: {pr: 42}`
- **THEN** шаг получает `42` вместо плейсхолдера

### Requirement: Сценарий pr-review

Система ДОЛЖНА содержать готовый сценарий `config/pipelines/pr-review.json`
с шагами: diff PR → изменённые файлы → RAG-поиск → генерация ревью
(формат «Баги / Архитектурные проблемы / Рекомендации», русский язык) →
публикация review в GitHub (event=COMMENT).

- Обращение к GitHub — только через MCP-сервер `github` (тулы
  `get_pull_request_diff`, `get_pull_request_files`,
  `create_and_submit_pull_request_review`).
- Усечённый diff ДОЛЖЕН явно помечаться в тексте ревью.
- Код PR не исполняется ни на одном шаге.

#### Scenario: ревью открытого PR
- **WHEN** пайплайн `pr-review` запущен с параметрами repo/pr
- **THEN** в GitHub появляется review с текстом ревью, статус пайплайна —
  success

#### Scenario: усечённый diff
- **WHEN** diff PR превышает кап результата тула
- **THEN** текст ревью содержит явную пометку, что проанализирована часть
  diff

### Requirement: Дедупликация ревью

Система ДОЛЖНА хранить факт опубликованного ревью
(`<dataDir>/pipeline/pr-review/{repo}#{pr}.json`: repo, pr, headSha,
reviewUrl) и при повторном запуске по тому же headSha возвращать
`409 {status: "skipped"}`, не публикуя повторного review.

#### Scenario: повторное событие того же коммита
- **WHEN** пайплайн `pr-review` запущен повторно по PR с тем же headSha
- **THEN** ответ 409 со статусом `skipped`, review в GitHub не дублируется

#### Scenario: новый коммит в PR
- **WHEN** пайплайн запущен по PR с новым headSha
- **THEN** ревью выполняется, запись обновляется

### Requirement: Мост GitHub Action

Репозиторий ДОЛЖЕН содержать workflow `.github/workflows/pr-review.yml`,
который на события `pull_request` (opened, synchronize) на self-hosted
runner'е запускает пайплайн через локальный API Штурмана и завершается
статусом пайплайна.

- Токен Штурмана НЕ хранится в GitHub (локальный runner обращается к
  localhost).
- Ответ 409 от API (запят/дедуп) — ретраи с бэкоффом, до 3 попыток.
- Отказ соединения — ошибка шага с сообщением «Штурман не запущен».
- Текст failed-шага пайплайна попадает в аннотацию ошибки workflow.

#### Scenario: автоматическое ревью на PR
- **WHEN** открывается новый PR в репозитории
- **THEN** workflow стартует на self-hosted runner'е, пайплайн публикует
  review, workflow завершается успехом

#### Scenario: бот не поднят
- **WHEN** workflow стартует при остановленном Штурмане
- **THEN** workflow краснеет с аннотацией «Штурман не запущен»
