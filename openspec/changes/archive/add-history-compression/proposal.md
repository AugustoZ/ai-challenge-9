# Изменение: компрессия истории диалога и режим сравнения

> Статус: implemented (архивирован 2026-09-13, capabilities переосмыслены и заменены
> change `add-context-strategies`). Capabilities: `history-compression`, `comparison-mode`.
> SDD-фиксация доработки; реализация идёт по `tasks.md` этого change.

## Зачем

В одиночных режимах (default, direct, step_by_step, agent) сервер отдаёт модели
всю историю сессии: контекст = system + история + новый запрос. На длинном
диалоге prompt_tokens растут с каждым сообщением, и львиная доля расхода
приходится на старые ходы, которые модель уже видела.

Компрессия истории: последние 5 сообщений уходят в запрос «как есть», более
старая история сворачивается в rolling summary (пересборка той же моделью
каждые 5 сообщений вне окна). Summary хранится отдельно на сессии и
подставляется в запрос вместо полной истории. Итог: prompt_tokens на длинном
диалоге стабилизируются, экономия видна в «Топливомере».

Вместе с компрессией добавляется зеркальный режим сравнения: один вопрос
прогоняется через две параллельные сессии (со сжатием и без), ответы и
расход токенов показываются side-by-side. Автоматической оценки качества
не вводится: пользователь смотрит на два ответа и расход сам.

## Ключевые решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | **Consume-and-store**: после merge слитые сообщения удаляются из `Session.messages` (операция хранилища `applyCompressionResult`), живут только в summary | Честный учёт токенов: prompt_tokens сжатой стороны реально падают. «Сжатие» только во view оставило бы хранилище растущим до кэпа 200 сообщений и сделало бы mirror-сравнение нечестным. Lossiness (сводка хуже оригинала) задокументирована как осознанный расход; деструктивный 200-кап (`trimSessionHistory`, SessionStore.kt) остаётся safety-net |
| 2 | **Синхронный merge до ответа** при пересечении порога | Асинхронный merge даёт гонку: ответ уходит по несжатой истории, summary появляется позже, и mirror-сравнение теряет детерминизм. Цена: один дополнительный LLM-вызов на порог (каждые mergeEvery=5 сообщений) ложится на сжатую сторону |
| 3 | **Токены суммаризатора относятся к сжатой стороне**, отдельным полем `ChatResponse.summaryTokens` | Суммаризатор работает на сжатой сессии, и его расход входит в экономику этой стороны. Смешивать его с токенами ответа нельзя: «экономия» завысилась бы |

Конфиг: `compressionEnabled` (default false), `compressionWindowSize=5`,
`compressionMergeEvery=5`, `compressionSummaryMaxTokens=400`. Приоритет:
поле запроса `ChatRequest.compressionEnabled` выше конфига.

## Edge cases

- **Turn-boundary guard.** Окно «последних 5» расширяется назад до ближайшего
  user-сообщения; пара assistant(tool_calls) → role="tool" не рвётся никогда,
  иначе провайдер отвечает 400. Тот же инвариант, что в `SessionHistory.trim`
  (SessionHistory.kt, гвард на L61-64).
- **Деструктивный 200-кап.** При consume-семантике история растёт медленно, и
  кап `Session.messages` (MAX_MESSAGES=200, `trimSessionHistory` в
  SessionStore.kt) становится страховкой на вырожденные случаи, а не основным
  механизмом управления длиной.
- **Oversized summary.** Бюджет summaryMaxTokens=400. Если сводка длиннее:
  один повторный вызов с инструкцией «сожми жёстче»; при повторном превышении
  жёсткая обрезка по границе предложений.
- **Сбой суммаризатора.** Ловится `runCatching`: сохраняется прежний summary,
  ответ возвращается как обычно, `summaryTokens=null`. Чат не падает из-за
  суммаризатора.
- **Переключение тумблера mid-session.** Флаг читается на каждый запрос. Выкл:
  запрос уходит модели с полной историей, существующий summary (если был) не
  подставляется. Вкл снова: merge продолжается с того же порога, batch может
  превысить mergeEvery (один merge закрывает всё накопившееся).
- **«н/д» при null usage.** Провайдер не вернул usage (например, протокол
  OpenCode) → в UI «н/д» вместо числа, в итоговой строке сравнения «н/д» на
  соответствующем месте. Не 0 и не NaN.

## Caveat: протокол OpenCode

У провайдера `type=opencode` протокол флаттенит историю сообщений в один
prompt: мультиролевая структура (ходы, tool-пары) до модели в таком виде не
доходит. Компрессия в этом случае работает: summary и окно вплетаются в тот
же флаттенед prompt, расход токенов падает. Но turn-boundary guard защищает
наши данные, а не то, что OpenCode передаст дальше; сам флаттенинг не
чинится, задокументирован как есть (одна строка KDoc в коде проводки).

## Что меняется (сводка)

- `Session`: новое поле `summary: String? = null`. Default обязателен:
  обратная совместимость со старыми файлами сессий (FileSessionStore парсит
  с `ignoreUnknownKeys`).
- Новый `session/HistoryCompressor.kt` (окно, порог, merge) +
  `client/SummaryPrompts.kt` (паттерн `JudgePrompts`) + интерфейс
  `HistorySummarizer` (фейкабелен в тестах, ноль сети).
- Конфиг: четыре compression-поля, `config.json` и `config.example.json`
  правятся синхронно.
- API: `ChatRequest.compressionEnabled: Boolean?`,
  `ChatResponse.summaryTokens: Int?`, `ChatResponse.summaryApplied: Boolean`.
- Фронтенд: тумблер «Сжатие истории» и зеркальный режим сравнения
  (twin-сессии, side-by-side, токены по каждой стороне).
- QA: `scripts/mock-llm.py` (детерминированный mock) + `config.dev.json`.
  Живой LLM-ключ ни в одном тесте и ни в одном QA-сценарии.

## Вне скоупа

- Пути Team и Prompt-to-Prompt (stateless) не трогаются: ни одного упоминания
  summary в их коде.
- Абстракция CompressionStrategy и реестр алгоритмов не вводятся: один
  конкретный компонент.
- LLM-as-judge для сравнения исключён: вердикт о качестве за пользователем.
- Mirror-прогоны не персистируются в Бортовой журнал; восстановление
  токен-истории при перезагрузке не чинится (существующий гэп, вне скоупа).
- Старые сессии не мигрируются: merge накроет их при следующем пороге.
