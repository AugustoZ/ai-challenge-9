# Изменение: стратегии управления контекстом «Штурман»

> Статус: draft. Capabilities: `context-strategy-switcher`, `sliding-window`,
> `facts-memory`, `branching`, `comparison-mode`.
> SDD-фиксация доработки; реализация идёт по `tasks.md` этого change.
> CLI `openspec` в среде не установлен — структура change проверена вручную.

## Зачем

Сегодня у «Штурмана» ровно один механизм управления длиной контекста:
«Сводка» (rolling summary, change `add-history-compression`) — lossy,
деструктивная (consume-and-store), и включается одним тумблером
`compressionEnabled`. Пользователь не может выбрать, **как** управлять
контекстом, и не может **сравнить** подходы на одном вопросе.

Итоговая модель: единый переключатель из 5 позиций — **Выкл / Окно /
Сводка / Факты / Ветки**:

- **Выкл** (off) — вся история в запрос, как было до компрессии;
- **Окно** (window) — последние 5 сообщений as-is, остальное не
  подставляется (non-destructive view);
- **Сводка** (summary) — реализованная в прошлой итерации rolling
  summary, поведение байт-в-байт;
- **Факты** (facts) — KV-память: блок ключ-значение с важными данными
  диалога + последние 3 сообщения;
- **Ветки** (branching) — автоматическое ветвление: система сама
  создаёт точку checkpoint и близнец-ветку каждые 5 user-сообщений,
  ветками переключаются.

Зеркальный режим обобщается: каждая колонка получает **любую** выбранную
стратегию (Ветки в колонках не участвует), заголовки колонок отражают
выбранные стратегии.

## Ключевые решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | **Пять стратегий, приоритет разрешения: явный `contextStrategy` запроса > legacy `compressionEnabled` > конфиг** | Поле запроса — высший приоритет, по прецеденту `compressionEnabled` прошлой итерации. Legacy-маппинг `compressionEnabled=true` без `contextStrategy` → summary байт-в-байт: старые клиенты и 173 существующих тестов не ломаются. Неизвестный id → 400 с внятным текстом |
| 2 | **Окно и Факты — non-destructive VIEW над `session.messages`; только Сводка деструктивна (consume-and-store)** | Асимметрия осознанно задокументирована: «Сводку» не трогаем (регрессия её пути = провал), Окно/Факты читают историю и не удаляют ничего. Последствие: переключение **со** «Сводки» на Окно/Выкл теряет историю за окном (сообщения уже удалены прошлым merge) — предупреждено в дельте switcher и в Edge cases |
| 3 | **Ветки — полностью автоматические: авто-форк каждые `branchCheckpointEvery` (default 5) user-сообщений, ручной форк не существует** | Форк срабатывает после завершения ответа ассистента: если в активную ветку добавлен N-й user-месседж **с момента создания ветки** (унаследованный префикс не считается — иначе каскадный форк у близнеца), система сама создаёт близнец (копия messages/summary/facts), активная продолжает. Счётчик ведётся отдельно для каждой ветки. Кап 8 веток на сессию: при достижении форк пропускается. Плоский селектор, дерево веток не строится |
| 4 | **Факты: read-only в UI, экстракция только при активной стратегии facts, сбой → прежние факты** | LLM-вызов экстракции — после завершения ответа ассистента, синхронно, ловится `runCatching`: при сбое сети/парсинга сохраняются прежние факты, ответ возвращается 200. LLM возвращает **полный** обновлённый KV-JSON (массив `[{key, value}]`, макс 10 фактов) — без инкрементальных патчей. В UI панель фактов read-only (ключ: значение), без ручной правки |
| 5 | **Зеркало — «стратегия на колонку»: любая пара из Выкл/Окно/Сводка/Факты, Ветки исключена** | Обобщение mirror-режима прошлой итерации: левая и правая колонки независимы. Twin-сессии никогда не получают стратегию branching → форк-движок в зеркале не активируется. Изоляция ошибок сторон сохранена: отказ оседает карточкой в своей колонке |

Конфиг: `contextStrategy` (default `off`), `branchCheckpointEvery`
(default 5). Приоритет: поле запроса выше конфига, выше legacy-флага.
Env-переменные для новых ключей НЕ добавляются (env-список проекта
зафиксирован). Параметры окна (5), фактов-окна (3) и капов — глобальный
конфиг и константы спецификации, per-request параметров нет.

## Edge cases

- **Переключение со «Сводки» на Окно/Выкл.** Слитые сообщения удалены
  consume-and-store и восстановлению не подлежат: за окном/сводкой
  история потеряна. Задокументировано в дельте `context-strategy-switcher`
  (требование о приоритете) и принято как следствие преемственной
  lossy-семантики прошлой итерации.
- **Неизвестный `contextStrategy`.** Значение вне набора
  off|window|summary|facts|branching → HTTP 400, запрос не
  обрабатывается, сессия не меняется.
- **Team и Prompt-to-Prompt.** Стратегия no-op (путь stateless), как
  компрессия в прошлой итерации: поле в этих режимах не действует.
- **Форк и tool-пары.** Срез/копия состояния на момент форка не рвёт
  пар assistant(tool_calls) → tool: близнец получает точную копию
  `messages`, и turn-boundary guard действует во всех срезах (окно,
  seed, view) по-прежнему.
- **Зеркало подавляет ветвление.** twin-сессии не шлют branching →
  checkpoint'ов в зеркальном прогоне нет, SSE-события `checkpoint` в
  twin-стримах не ожидается.
- **Наследуемый префикс ветки.** Близнец получает копию истории, но
  счётчик его user-сообщений начинается с нуля: первые N наследованных
  сообщений его собственный форк не спровоцируют.

## Caveat: протокол OpenCode

У провайдера `type=opencode` протокол флаттенит историю в один prompt —
мультиролевая структура до модели в этом виде не доходит. Стратегии
работают на **нашем** виде запроса (окно, факты-блок, история ветки
собираются корректно и вплетаются во флаттенед prompt), но
turn-boundary guard защищает наши данные, а не то, что OpenCode
передаст дальше. Флаттенинг не чинится, задокументирован как есть —
те же оговорки, что у компрессии в прошлой итерации.

## Что меняется (сводка)

- Новый enum `ContextStrategy` (off|window|summary|facts|branching) +
  resolve-логика; `ChatRequest.contextStrategy`/`branchId`,
  `ChatResponse.contextStrategy`/`branchId`/`facts` (echo,
  `@EncodeDefault(ALWAYS)`); конфиг `contextStrategy`/`branchCheckpointEvery`.
- `session/SessionStore.kt` (+File): `Branch`, `Fact`, поля
  `Session.branches`/`activeBranchId`/`branchSeq`/`facts`, операции
  fork/activate/setFacts; back-compat старых JSON (чтение да, миграция
  нет).
- `ContextPlanner` — view по разрешённой стратегии; `sliceWindow`
  извлечён в свободную функцию (семантика гвардов не меняется).
- `FactExtractor`: промпты + LLM-реализация + seam-factory по образцу
  `summarizerFactory`; экстракция после ответа только при стратегии
  facts.
- `routes/Routes.kt`: разрешение стратегии, авто-форк, эндпоинты
  `GET /api/session/{id}/branches`,
  `POST /api/session/{id}/branches/activate`, SSE-событие `checkpoint`
  (non-terminal).
- Фронтенд: радио-переключатель 5 позиций, панель фактов read-only,
  маркеры checkpoint в ленте + плоский селектор веток, зеркало
  «стратегия на колонку» с labels.
- QA: `scripts/mock-llm.py` + маркер «Извлечение фактов»; ноль живого
  LLM в тестах и QA.

## Вне скоупа

- LLM-as-judge для сравнения стратегий (вердикт за пользователем).
- RAG / внешние источники знаний.
- Ручное ветвление, переименование, удаление и merge веток, дерево
  веток — только авто-форк и плоский селектор.
- Per-request параметры окна/фактов/бюджета — только глобальный конфиг.
- Новые env-переменные (список зафиксирован).
- Миграция/бэкфилл старых сессий (back-compat чтения — да, перезапись —
  нет).
- JS-тест-харнесс для фронтенда (QA: `node --check` + Playwright).
- Пути Team и Prompt-to-Prompt, кроме зафиксированного no-op.
