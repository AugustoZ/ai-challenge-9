# Спецификация: assistant-invariants

> Дельта change `assistant-invariants`. Новая capability.

## ADDED Requirements

### Requirement: Хранение глобальных инвариантов

Глобальные инварианты живут в отдельном файловом сторе `GlobalInvariantStore`
(`<dataDir>/invariants.json`, форма `{"invariants":[{id, text}, …]}`),
отдельно от диалога. Запись атомарная (tmp + ATOMIC_MOVE), мутации
синхронизированы; отсутствующий или повреждённый файл читается как пустой
дефолт, а не исключение (последующий `add` перезаписывает файл валидным
JSON). Стор использует собственный `Json { ignoreUnknownKeys = true }`.
Форма записи — `StoredInvariant(id: String, text: String)`, где `id` —
стабильный UUID, создаваемый при добавлении. Валидация при добавлении:
текст 1..300 символов после trim, не более 20 инвариантов на скоуп, точный
дубль текста после trim отклоняется (E3, E4).

#### Scenario: Round-trip через глобальный стор

- КОГДА инвариант добавлен через `add`, прочитан через `list` и удалён
  через `remove`
- ТОГДА список содержит добавленный инвариант с тем же id и text, а после
  удаления — без него
- И изменение переживает пересоздание стора по тому же каталоге

#### Scenario: Corrupt-файл — пустой дефолт

- КОГДА в каталоге данных лежит invariants.json с невалидным JSON
- ТОГДА `list()` возвращает пустой список без исключения
- И следующий `add` успешен, файл перезаписан валидным JSON

#### Scenario: Дубль и превышение капов отклоняются

- КОГДА `add` получает точный дубль текста после trim, текст длиннее 300
  символов, пустой/whitespace-текст или 21-й инвариант скоупа
- ТОГДА добавление отклонено (ошибка валидации с причиной)
- И список инвариантов не меняется

### Requirement: Хранение сессионных инвариантов

Сессионные инварианты хранятся в отдельном поле
`Session.invariants: List<StoredInvariant> = emptyList()`, а не как
сообщения внутри `Session.messages`. Поле живёт и умирает вместе с сессией.
Default обязателен: старые файлы сессий без этого поля загружаются с
emptyList (дефолт поля — back-compat, `ignoreUnknownKeys` — rollback; E2).
Операции хранилища `updateInvariants(sessionId, invariants)` и
`getInvariants(sessionId)` реализованы в InMemory- и File-сторах;
неизвестная сессия — тихий no-op без исключения. Снимки веток (Branch)
инварианты не содержат: состояние общее на сессию (осознанное ограничение,
KDoc на Branch; E11, G6).

#### Scenario: Старый файл сессии без поля invariants

- КОГДА загружается JSON сессии, записанный до появления поля
- ТОГДА сессия загружается без ошибки
- И `getInvariants` возвращает пустой список

#### Scenario: Round-trip через стор сессии

- КОГДА инварианты записаны через `updateInvariants` и прочитаны через
  `getInvariants` (InMemory или FileSessionStore)
- ТОГДА прочитанный список совпадает с записанным (id, text, порядок)
- И снапшот сессии содержит инварианты

#### Scenario: Ветка не захватывает инварианты

- КОГДА в сессии с непустыми invariants создаётся снимок ветки (Branch)
- ТОГДА снимок ветки не содержит invariants
- И инварианты остаются общими на сессию

#### Scenario: Неизвестная сессия — тихий no-op

- КОГДА `updateInvariants` или `getInvariants` вызваны с несуществующим
  sessionId
- ТОГДА исключений нет (`updateInvariants` → null, `getInvariants` →
  пустой список)
- И инварианты других сессий не затрагиваются

### Requirement: Инъекция блока в промпт

Каждый ход агентного режима сервер подставляет в промпт (seed
`handleAgent`) эфемерную system-строку с инвариантами: 4-й tail-слот,
после предпочтений и состояния задачи, до памяти; позиция — ПОСЛЕ trim
(G10). Строка не пишется в `Session.messages`. Форма блока: маркер
`НЕПРЕЛОЖНЫЕ ИНВАРИАНТЫ (нарушать запрещено)`, секции «Глобальные:» и
«Сессия:» (пустая секция опускается), нумерованные строки, затем константа
`REFUSAL_INSTRUCTION` (отказаться от конфликтующего запроса, назвать
инвариант, объяснить причину). При обоих пустых скоупах блок не
инъектируется вовсе (G8). Кап блока ~2000 символов, переполнение →
эллипсис (E10). Саб-вызовы (экстрактор, сводка, судья) блок не получают
(G2). Комментарий порядка в `handleAgent` обновляется: предпочтения →
состояние → инварианты → память (Q5).

#### Scenario: Блок в исходящем запросе

- КОГДА есть один глобальный и один сессионный инвариант, и пользователь
  отправляет сообщение
- ТОГДА запрос к модели содержит system-строку с маркером, обоими текстами
  и текстом `REFUSAL_INSTRUCTION`
- И после хода строка не присутствует в истории сессии

#### Scenario: Пустые скоупы — блока нет

- КОГДА инвариантов нет ни в одном скоупе
- ТОГДА запрос к модели не содержит строки с маркером «НЕПРЕЛОЖНЫЕ
  ИНВАРИАНТЫ»
- И `ChatResponse.invariants` == null

#### Scenario: Выживание при давлении контекста

- КОГДА история сессии длинная (выше порога trim) и инварианты непустые
- ТОГДА блок инвариантов присутствует в исходящем запросе (приоритет
  упаковки свежих групп в trimContext)
- И ни один tail-блок не вытеснен им

#### Scenario: Саб-вызовы не получают блок

- КОГДА в ходе хода выполняются саб-вызовы (экстрактор фактов, сводка,
  судья)
- ТОГДА их запросы не содержат строки с маркером инвариантов
- И поведение саб-вызовов не меняется

### Requirement: Chat-команды инвариантов

Команды обрабатываются ДО LLM-вызова и только с начала сообщения (после
trim + lowercase). Exact «инварианты»/«/инварианты» проверяется ПЕРВЫМ —
префикс не глотает команду списка (E6). Префиксы «инвариант »/«/инвариант »
(с пробелом) добавляют сессионный инвариант; «убери инвариант »/«/убери
инвариант » удаляют по 1-based номеру (только цифры). Команды управляют
только session-scope; глобальные управляются панелью (пометка в списке).
LLM для команд не вызывается; команда не добавляется в историю как
user-сообщение (поведение истории — точное зеркало существующего
pre-LLM-обработчика команд). Ошибки валидации (капы, дубли, E3/E4) и номер
вне диапазона/не число (E8) → системный ответ с причиной/подсказкой, 200,
без исключения. Ответы команд содержат invariants echo.

#### Scenario: Добавление командой без вызова LLM

- КОГДА пользователь отправляет «инвариант Только Kotlin»
- ТОГДА возвращается подтверждение с текстом инварианта, и echo ответа
  содержит его в session-скоупе
- И вызовов LLM нет

#### Scenario: Список: exact не съедается префиксом

- КОГДА пользователь отправляет «инварианты»
- ТОГДА возвращается нумерованный список сессионных инвариантов (1..N) и
  глобальные отдельным блоком без номеров с пометкой «управляются через
  панель»
- И вызовов LLM нет

#### Scenario: Удаление по номеру

- КОГДА пользователь отправляет «убери инвариант 1» при непустом
  session-scope
- ТОГДА первый сессионный инвариант удалён, подтверждение + echo без него
- И «убери инвариант 99» или «убери инвариант абв» → мягкий системный
  ответ с примером (200), не ошибка

#### Scenario: Команда в середине сообщения — обычный путь

- КОГДА пользователь отправляет «объясни, что такое инварианты»
- ТОГДА сообщение уходит в LLM (обычный путь)
- И перехват команды не происходит

### Requirement: API управления инвариантами

Пять роутов, все защищены (401 без валидного токена, включая
garbage-токены), внесены в таблицу защищённых маршрутов и в
`AuthInterceptTest`. Контракт: GET `/api/invariants?sessionId={id}` → 200
`{global, session}` | 400 (нет `sessionId`) | 404 (неизвестная сессия);
POST `/api/invariants/global` body `{text}` → 200 `{global}` | 400
(валидация/дубль/кап); DELETE `/api/invariants/global/{id}` → 200
`{global}` | 404 (неизвестный id); POST `/api/invariants/session` body
`{sessionId, text}` → 200 `{session}` | 400 | 404; DELETE
`/api/invariants/session/{sessionId}/{id}` → 200 `{session}` | 404
(неизвестная сессия или id). Формат ошибок — `{"error": "…"}`, текст на
русском (E5).

#### Scenario: 401 без токена

- КОГДА любой из 5 роутов вызван без токена или с garbage-токеном
- ТОГДА ответ 401
- И данные не изменяются

#### Scenario: CRUD-успех

- КОГДА последовательно: POST global `{text}` → GET `?sessionId` → POST
  session `{sessionId, text}` → GET → DELETE global/{id} → DELETE
  session/{sessionId}/{id} → GET
- ТОГДА каждый успешный вызов отвечает 200 с актуальным списком своего
  скоупа
- И финальный GET показывает оба пустых списка

#### Scenario: Ошибки валидации — 400

- КОГДА GET без `sessionId`, POST пустого текста, POST 301 символа, POST
  точного дубля, POST 21-го инварианта
- ТОГДА ответ 400 с сообщением на русском в формате `{"error": "…"}`
- И состояние сторов не меняется

#### Scenario: Неизвестная сессия и id — 404

- КОГДА GET/POST session с неизвестным sessionId или DELETE с неизвестным
  id (любой скоуп)
- ТОГДА ответ 404
- И данные других сессий и глобального стора не затрагиваются

### Requirement: Echo инвариантов в ответе

Контракт `ChatResponse` содержит поле `invariants: InvariantsPayload?`,
где `InvariantsPayload = {global: Invariant[], session: Invariant[]}`,
`Invariant = {id, text}` (зеркало Kotlin-типов в `types.ts`). Поле
заполняется каждым data-bearing ответом — обычным (LLM) и командным;
когда оба скоупа пусты, значение — null. Поле nullable с дефолтом: старые
клиенты совместимы.

#### Scenario: Echo каждым ходом

- КОГДА инварианты есть хотя бы в одном скоупе и пользователь отправляет
  сообщение
- ТОГДА ChatResponse содержит invariants с актуальными обоими скоупами
- И фронтенд получает их без отдельного запроса

#### Scenario: Пустые скоупы — null

- КОГДА инвариантов нет ни в одном скоупе
- ТОГДА `ChatResponse.invariants` == null
- И старые клиенты не ломаются (поле отсутствует/пусто)

### Requirement: Отказ через промпт-инструкцию

Механизм отказа — промпт-инструкция, а не механическая блокировка:
инъектированный блок содержит константу `REFUSAL_INSTRUCTION` — при
запросе, противоречащем инварианту, модель вежливо отказывается, называет
нарушенный инвариант и кратко объясняет причину. Сервер не детектирует, не
маркирует и не блокирует такие ответы (G3). Качество отказа оценивается
non-CI rubric (процедура в proposal, Q2) и не является
acceptance-критерием; CI-бар механический: инъекция, константа, trim,
passthrough (Q1).

#### Scenario: Инструкция в промпте

- КОГДА блок инвариантов инъектирован в ход
- ТОГДА system-строка содержит константу `REFUSAL_INSTRUCTION` с запретом
  нарушать и обязанностью назвать инвариант и объяснить причину
- И тесты проверяют её наличие по константе кода, а не по полному рендеру

#### Scenario: Passthrough — механической блокировки нет

- КОГДА модель отвечает текстом, нарушающим инвариант (mock-режим
  `violate`)
- ТОГДА ответ возвращается клиенту как обычный, без серверной блокировки,
  маркеров или изменений истории
- И echo в ответе не искажается

#### Scenario: Детерминированный mock-отказ

- КОГДА mock-режим `refuse` и в system присутствует маркер «НЕПРЕЛОЖНЫЕ
  ИНВАРИАНТЫ»
- ТОГДА ответ — отказ с цитированием инварианта
- И при отсутствии маркера в system refuse отвечает обычным
  ротационным ответом (детерминированный тест инъекции)
