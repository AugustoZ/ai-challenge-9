# Спецификация: comparison-mode

> Дельта change `add-history-compression`. Новая capability.

## ADDED Requirements

### Requirement: Twin-сессии для сравнения

При включённом зеркальном режиме фронтекст отправляет каждое сообщение в
пару twin-сессий: `twinFull` (compressionEnabled=false, история полная) и
`twinComp` (compressionEnabled=true, компрессия включена). Запросы идут
параллельно на существующий `POST /api/chat/stream`; новых эндпоинтов на
сервере нет. Id сессий обеих сторон выдаёт сервер и возвращается в ответе;
состояние mirror (id, накопленные токены) живёт в JS-памяти страницы.

#### Scenario: Первое сообщение в зеркальном режиме

- КОГДА пользователь включает тумблер «Режим сравнения» и отправляет
  сообщение
- ТОГДА уходят два параллельных запроса /api/chat/stream (twinFull и
  twinComp) с одинаковым текстом
- И id обеих twin-сессий получены из ответов сервера

#### Scenario: Последующие сообщения

- КОГДА зеркальный режим включён и отправляется следующее сообщение
- ТОГДА оба twins получают его, id сессий переиспользуются

#### Scenario: Выключение режима

- КОГДА тумблер «Режим сравнения» выключен
- ТОГДА сравнение завершается, twin-сессии остаются в списке
  /api/sessions как обычные
- И основной диалог и его счётчики не затронуты

### Requirement: Side-by-side рендер

Результат сравнения рендерится блоком-сеткой `.mirror-grid` под чатом: две
колонки `.mirror-col[data-side="full"]` («Без сжатия») и
`.mirror-col[data-side="compressed"]` («Со сжатием»). В каждой колонке
собственный ответ и собственная строка топлива.

#### Scenario: Обе стороны ответили

- КОГДА оба mirror-запроса завершены успешно
- ТОГДА в обеих колонках непустые ответы
- И в каждой колонке строка «Топливо: запрос X + ответ Y» со своими
  числами

### Requirement: Токены по каждой стороне, summaryTokens отдельно

Накопленный итог токенов считается раздельно для каждой стороны. Сжатая
сторона дополнительно показывает расход вызова суммаризатора
(`ChatResponse.summaryTokens`) в своей строке топлива («+сводка: N») и в
итоговой строке. Итоговая строка под сеткой: оба итога и экономия в
процентах.

#### Scenario: Сводка применена на сжатой стороне

- КОГДА сжатая сторона выполнила merge
- ТОГДА строка топлива её колонки содержит «+сводка: N»
- И итоговая строка содержит токены обеих сторон и экономию

### Requirement: «н/д» при отсутствии usage

Если провайдер не вернул usage (поле токенов null), UI показывает «н/д»
вместо числа: не 0, не NaN, не пустую строку. Правило действует и в строках
топлива колонок, и в итоговой строке сравнения.

#### Scenario: Одна сторона без usage

- КОГДА на одной из сторон tokens == null (например, протокол
  type=opencode не отдаёт usage)
- ТОГДА в строке топлива этой колонки и в итоговой строке «н/д»
- И числа второй стороны показаны как есть

### Requirement: Изоляция ошибок сторон

Ошибка одной стороны mirror (сеть, 5xx, таймаут) показывается только в её
колонке карточкой с текстом ошибки. Вторая сторона рендерится нормально,
страница не падает, необработанных исключений в консоли нет.

#### Scenario: Одна сторона упала

- КОГДА один из mirror-запросов завершился ошибкой
- ТОГДА в её колонке карточка ошибки
- И в колонке второй стороны нормальный ответ с топливом

### Requirement: Оценка качества за пользователем

Режим сравнения не вводит автоматической оценки качества (LLM-as-judge
исключён): пользователь сам смотрит на ответы обеих сторон и на расход
токенов. UI не выносит вердикт о том, какой ответ лучше.

#### Scenario: Сравнение завершено

- КОГДА оба ответа отрисованы
- ТОГДА UI показывает ответы и метрики обеих сторон
- И в нём нет автоматического вердикта о качестве
