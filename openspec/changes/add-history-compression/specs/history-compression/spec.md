# Спецификация: history-compression

> Дельта change `add-history-compression`. Новая capability.

## ADDED Requirements

### Requirement: Окно последних 5 сообщений as-is с turn-boundary guard

Контекст одиночных режимов (default, direct, step_by_step, agent) содержит
окно из последних `compressionWindowSize` (default 5) сообщений истории
сессии без изменений. Если граница окна наезжает на message с role="tool"
(его assistant(tool_calls) остался за границей), окно расширяется назад до
ближайшего предшествующего role="user". assistant(tool_calls), попавший на
границу, безопасен, пока его tool-ответ лежит внутри окна. Пара
assistant(tool_calls) → role="tool" не разрывается никогда: в окне не
появляется role="tool" без предшествующего assistant(tool_calls).

#### Scenario: Окно короче порога merge

- КОГДА в сессии 7 сообщений, windowSize=5, summary ещё нет
- ТОГДА в запрос уходит последние 5 сообщений as-is
- И merge не выполняется

#### Scenario: Срез окна наезжает на tool-сообщение

- КОГДА сообщение в позиции «5-е с конца» имеет role="tool", а её
  assistant(tool_calls) лежит раньше
- ТОГДА окно расширяется назад до ближайшего user-сообщения
- И в окне нет role="tool" без предшествующего assistant(tool_calls)

### Requirement: Порог mergeEvery, один merge на все накопившиеся

Merge (пересборка сводки) срабатывает, когда число сообщений вне окна
не меньше `compressionMergeEvery` (default 5). Один merge закрывает все
сообщения, оказавшиеся вне окна к этому моменту, а не только порог: при
пересечении нескольких порогов за раз вызов суммаризатора один. Батч
суммаризации предварительно обрезается до
`HistoryCompressor.SUMMARY_BATCH_TOKEN_BUDGET` (12 000 оценочных токенов),
отбрасывая старейшие ходы целиком по user-границам; `removeCount` при этом
равен всему накопившемуся вне окна, а не размеру обрезанного батча.

#### Scenario: Порог не достигнут

- КОГДА вне окна 4 сообщения, mergeEvery=5
- ТОГДА merge не выполняется
- И прежний summary (если был) остаётся без изменений

#### Scenario: Накопилось больше порога

- КОГДА вне окна 12 сообщений, mergeEvery=5
- ТОГДА вызов суммаризатора ровно один
- И removeCount в результате равен 12 (всё накопившееся вне окна)
- И переданный суммаризатору батч укладывается в
  SUMMARY_BATCH_TOKEN_BUDGET: если 12 сообщений вместе превышают бюджет,
  старейшие ходы отброшены по user-границе

### Requirement: Oversized summary: один retry, затем жёсткая обрезка

Если полученная сводка длиннее `compressionSummaryMaxTokens` токенов
(оценка — единственный эстиматор chars/2.5), выполняется ОДИН повторный
вызов суммаризатора: инструкция «сожми жёстче» и черновик oversized-сводки
передаются в параметре `previous`. Если повторная сводка всё ещё превышает
бюджет, текст жёстко обрезается до `summaryMaxTokens * 2.5` символов с
откатом к ближайшему знаку конца предложения (`.`, `!`, `?`, `\n`).

#### Scenario: Сводка превысила бюджет

- КОГДА первая сводка длиннее summaryMaxTokens
- ТОГДА выполняется второй вызов суммаризатора с инструкцией «сожми жёстче»
- И итоговая сводка не длиннее summaryMaxTokens (второй результат либо
  hardCut)

### Requirement: Summary хранится отдельным полем сессии

Сводка хранится в отдельном поле `Session.summary: String? = null`, никогда
не как сообщение внутри `Session.messages`. До первого merge поле null.
Default обязателен: старые файлы сессий без этого поля загружаются.

#### Scenario: Старый файл сессии без поля summary

- КОГДА загружается JSON сессии, записанный до появления поля
- ТОГДА сессия загружается без ошибки
- И summary == null

#### Scenario: Удаление или очистка сессии сбрасывает summary

- КОГДА сессия удалена или история очищена
- ТОГДА её summary исчезает вместе с ней (поле живёт на сессии,
  отдельного хранилища для сводок нет)

### Requirement: Consume: слитые сообщения удаляются из хранилища

После успешного merge записанный summary заменяет исходные сообщения:
операция хранилища `applyCompressionResult(sessionId, newSummary,
removeCount)` устанавливает summary и удаляет первые removeCount сообщений
из `Session.messages` атомарно (паттерн блокировок `append`).

#### Scenario: Merge укорачивает историю в хранилище

- КОГДА merge выполнен с removeCount=12 у сессии из 17 сообщений
- ТОГДА в хранилище summary непусто
- И сообщений осталось 5 (окно)
- И удалённые сообщения в истории отсутствуют

### Requirement: SessionHistory.trim остаётся stage-2 после инъекции summary

Существующий `SessionHistory.trim` (бюджет MAX_HISTORY_TOKENS=24000 с
резервом под «Топливо» и новый запрос) применяется ПОСЛЕ сборки вида
запроса: сначала planView (summary как system-сообщение + окно), затем
trim. Trim не вызывается до инъекции summary и не заменяется ею.

#### Scenario: Summary + окно превышают бюджет

- КОГДА оценка summary + окно + новый запрос выходит за
  MAX_HISTORY_TOKENS минус резерв
- ТОГДА trim отрезает старые целые ходы вида запроса
- И запрос уходит в модель с обрезанным видом, а не падает с 400

### Requirement: Сбой суммаризатора не ломает чат

Ошибка вызова суммаризатора (сеть, 5xx провайдера, битый ответ) ловится
`runCatching`: сохраняется прежний summary, основной ответ возвращается
как обычно, `summaryTokens` в ответе null.

#### Scenario: Провайдер суммаризации недоступен

- КОГДА запрос на суммаризацию завершился ошибкой при пересечённом пороге
- ТОГДА /api/chat отвечает 200 с непустым ответом
- И прежний summary (если был) сохранён в сессии
- И summaryTokens == null в ответе

### Requirement: Приоритет поля запроса выше конфига

Флаг компрессии решается на каждый запрос: непустое поле
`ChatRequest.compressionEnabled` перекрывает значение конфига
`compressionEnabled`; поле null → берётся конфиг.

#### Scenario: Конфиг вкл, запрос явно выкл

- КОГДА config compressionEnabled=true, а в запросе
  compressionEnabled=false
- ТОГДА запрос идёт без компрессии: merge не выполняется, summary не
  подставляется

#### Scenario: Поле запроса отсутствует

- КОГДА запрос не несёт compressionEnabled (null)
- ТОГДА действует значение из конфига
