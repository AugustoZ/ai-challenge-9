# Спецификация: Модель памяти (memory layers)

## ADDED Requirements

### Requirement: Три слоя памяти с раздельным хранением

Система MUST хранить память агента в трёх независимых слоях: краткосрочная
(ходы диалога и сводка — существующее хранилище сессий), рабочая (данные
текущей задачи — `dataDir/working/{sessionId}.json`, по файлу на сессию),
долговременная (профиль/решения/знания — `dataDir/memory/longterm.json`,
глобальный файл). Слои MUST быть доступны независимо: чтение одного слоя не
требует наличия файлов других.

#### Scenario: Первый запуск без файлов памяти
- **WHEN** приложение стартует при пустых `dataDir/working` и `dataDir/memory`
- **THEN** оба слоя считаются пустыми без ошибок в логах, приложение работает

#### Scenario: Удаление сессии чистит рабочую память
- **WHEN** сессия удаляется через `DELETE /api/session/{id}`
- **THEN** файл `dataDir/working/{sessionId}.json` удалён, записи недоступны

### Requirement: Рабочая память — сессионный скратчпад

Рабочая память MUST поддерживать до 24 записей `{id, title, content, createdAt,
updatedAt}` (title ≤ 120, content ≤ 4000 символов) с CRUD через инструмент
`task_notes`, HTTP API и панель UI. Записи рабочей памяти MUST быть общими для
всех веток сессии. Превышение капов MUST возвращать ошибку (инструмент —
`ok=false` с текстом о лимите; API — 400).

#### Scenario: Агент сохраняет заметку задачи
- **WHEN** агент вызывает `task_notes` с `{"action":"add","title":"Шаг 1","content":"..."}`
- **THEN** запись сохранена в `dataDir/working/{sessionId}.json`, инструмент
  подтверждает с id; при следующем обращении к модели заметка в блоке памяти

#### Scenario: Переполнение капа записей
- **WHEN** в рабочей памяти уже 24 записи и агент вызывает `task_notes action=add`
- **THEN** инструмент отвечает `ok=false` с текстом «лимит 24 записи»; счётчик не меняется

#### Scenario: Ручное управление в UI
- **WHEN** пользователь в оверлее «Память» на вкладке «Рабочая» добавляет,
  правит, удаляет записи или жмёт «Очистить»
- **THEN** изменения сохраняются на сервере и видны агенту при следующем ходе

### Requirement: Долговременная память — глобальный магазин знаний

Долговременная память MUST поддерживать до 200 записей `{id, kind: profile|
decision|knowledge, title, content, tags, source: user|agent, createdAt,
updatedAt}` (title ≤ 120, content ≤ 2000, tags ≤ 8×24). Запись MUST проходить
через инструмент `memory_save`, API или UI; чтение/поиск — через `memory_recall`,
API или UI (фильтр по виду + поиск по подстроке).

#### Scenario: Агент сохраняет решение по явной просьбе
- **WHEN** пользователь пишет «запомни: для деплоя используем порт 8083» и агент
  вызывает `memory_save` с `{"kind":"decision","title":"Порт деплоя","content":"..."}`
- **THEN** запись сохранена с `source: agent` и видна в панели «Долговременная»

#### Scenario: Поиск по памяти
- **WHEN** агент вызывает `memory_recall` с `{"query":"порт деплой"}`
- **THEN** инструмент возвращает найденные записи (title/tags/content содержат
  ключевые слова), отсортированные по релевантности

### Requirement: Инъекция памяти в контекст агента

При `memoryTools ≠ false` и наличии записей система MUST добавлять к семени
агентного цикла отдельное system-сообщение с блоком памяти ПОСЛЕ обрезки
истории (позиция: последним сообщением семени): секция «Долговременная память»
(все `profile`, кап 10; до 6 релевантных `decision`/`knowledge` по keyword-score
по сообщению пользователя) и секция «Рабочая память» (все записи, свежие сверху).
Бюджеты: 1800 символов LTM, 2400 — WM. Пустые секции опускаются; оба слоя
пусты — сообщения нет.

#### Scenario: Блок памяти присутствует при непустых слоях
- **WHEN** в долговременной есть запись с kind=`profile`, в рабочей — заметка,
  пользователь отправляет сообщение (memoryTools включён)
- **THEN** запрос к LLM содержит system-сообщение с обеими секциями после
  сообщения пользователя

#### Scenario: Пустая память — блока нет
- **WHEN** оба слоя памяти пусты
- **THEN** запрос к LLM не содержит блока памяти (число сообщений как раньше)

### Requirement: Явное управление памятью пользователем

Пользователь MUST управлять памятью через: (а) тумблер «Инструменты памяти
агента» в настройках (по умолчанию ВКЛ; выключен — инструменты не видны модели,
блок не инъецируется, панели UI работают); (б) ручной CRUD обеих панелей;
(в) видимость источника записей (`user`/`agent`).

#### Scenario: Тумблер выключен
- **WHEN** настройка «Инструменты памяти агента» ВЫКЛ и пользователь отправляет сообщение
- **THEN** запрос к LLM не содержит инструментов памяти и блока памяти; записи
  слоёв не теряются; панели UI продолжают работать

### Requirement: API памяти

- Рабочая: `GET/PUT /api/session/{id}/working` (PUT: `{id?, title, content}` —
  upsert), `DELETE /api/session/{id}/working/{entryId}`, `DELETE /api/session/{id}/working`.
- Долговременная: `GET /api/memory?kind=&q=`, `POST /api/memory`, `PUT/DELETE /api/memory/{id}`.
- Обзор: `GET /api/memory/overview?sessionId=` — счётчики трёх слоёв.
- Ошибки: 400 — некорректный kind/капы; 404 — неизвестная сессия/запись.

#### Scenario: Некорректный вид записи
- **WHEN** `POST /api/memory` с `{"kind":"other", ...}`
- **THEN** ответ 400 с текстом о допустимых видах (profile/decision/knowledge)

### Requirement: Нерегрессия существующего поведения

Слои памяти MUST NOT влиять на стратегии контекста (окно/сводка/факты), ветки,
учёт токенов и формат существующих ответов. Запросы без поля `memoryTools`
MUST трактоваться как включённая память (обратная совместимость).

#### Scenario: Старый клиент без memoryTools
- **WHEN** `POST /api/chat` без поля `memoryTools` (текущий фронт или curl)
- **THEN** память включена: инструменты и блок присутствуют при непустых слоях
