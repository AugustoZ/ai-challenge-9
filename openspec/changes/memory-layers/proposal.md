# Change: Модель памяти «Штурмана» (memory layers)

## Зачем

У агента сейчас единый «сваленный» контекст: ходы диалога (+ сводка/факты/ветки
по стратегии) живут в сессии, а знания, которые должны переживать сессии
(профиль пользователя, принятые решения, наработанные знания), нигде не
хранятся. Данные текущей задачи агенту приходится держать в контексте диалога,
откуда они вымываются компрессией.

Нужна явная модель памяти из трёх слоёв с раздельным хранением и явным
пользовательским управлением: что и куда сохраняется.

## Модель памяти (три слоя)

| Слой | Что хранит | Где живёт | Жизненный цикл |
|------|------------|-----------|----------------|
| Краткосрочная | Ходы текущего диалога (+ rolling-сводка) | Существующее хранилище сессий (`dataDir/sessions/{id}.json`) | Живёт в сессии; управляется стратегиями контекста (окно/сводка) |
| Рабочая | Данные текущей задачи: заметки, промежуточные результаты | НОВОЕ: `dataDir/working/{sessionId}.json` — по файлу на сессию | Сессионная: пустая у новой сессии; чистится при удалении сессии |
| Долговременная | Профиль, решения, знания | НОВОЕ: `dataDir/memory/longterm.json` — один глобальный файл | Переживает сессии; управляет пользователь |

## Ключевые решения

1. **Раздельное хранение — физическое.** Рабочая память — отдельный файл на
   сессию (`dataDir/working/{sessionId}.json`, атомарная запись tmp+rename как
   у FileSessionStore). Долговременная — отдельный глобальный файл
   (`dataDir/memory/longterm.json`). Краткосрочная — существующие файлы сессий.
   Слои не смешиваются ни в хранилище, ни в API.
2. **Записи памяти — типизированные структуры, не свободный текст.**
   Рабочая: `{id, title, content, createdAt, updatedAt}`. Долговременная:
   `{id, kind: profile|decision|knowledge, title, content, tags,
   source: user|agent, createdAt, updatedAt}`.
3. **Инструменты агента — трое**: `task_notes` (CRUD рабочей памяти; рабочая
   зона агента по умолчанию), `memory_save` и `memory_recall` (долговременная;
   только по явной просьбе пользователя — дисциплина фиксируется в системном
   промте). Реестр инструментов доукомплектовывается per-request в `handleAgent`
   (инструментам нужен sessionId и сторы; базовый реестр из конфига неизменяем).
4. **Инъекция в контекст — отдельным system-сообщением ПОСЛЕ trim** семени
   цикла: `[system(промт), user(вопрос), system(память)]`. Не режется
   `SessionHistory.trim`, пересобирается на каждый вызов LLM, пустые секции
   опускаются, оба слоя пусты — сообщения нет. Состав блока: долговременная =
   все записи `profile` (кап 10) + top-K=6 релевантных `decision`/`knowledge`
   по ключевым словам запроса (токены ≥3 символов, рус+лат, score по
   title+tags+content); рабочая = все записи (свежие сверху). Бюджеты:
   LTM ≤ 1800 символов, WM ≤ 2400 символов (лишнее отбрасывается с конца).
5. **Явный выбор пользователя — на трёх уровнях.**
   а) Тумблер настроек «Инструменты памяти агента» (по умолчанию ВКЛ):
   выключен → у агента нет инструментов памяти и блок памяти не инъецируется
   (панели UI продолжают работать). Передаётся в `ChatRequest.memoryTools:
   Boolean?` (null → ВКЛ; старые клиенты/конфиг совместимы).
   б) Кнопка «Память» в верхней полосе → оверлей с тремя вкладками
   (Краткосрочная / Рабочая / Долговременная): просмотр, добавление, правка,
   удаление, очистка рабочей — всё вручную.
   в) Дисциплина промта: агент пишет ТОЛЬКО по явной просьбе
   пользователя («запомни», «сохрани»); в рабочую — свободно в рамках задачи.
6. **Капы и валидация (отказ, не молча).** Рабочая: ≤ 24 записей, title ≤ 120,
   content ≤ 4000 символов. Долговременная: ≤ 200 записей, title ≤ 120,
   content ≤ 2000, tags ≤ 8×24, kind — только три значения. Превышение —
   ошибка в ответе инструмента / HTTP 400.
7. **API.** Рабочая: GET/PUT `/api/session/{id}/working`, DELETE
   `/api/session/{id}/working/{entryId}`, DELETE `/api/session/{id}/working`.
   Долговременная: GET/POST `/api/memory`, PUT/DELETE `/api/memory/{id}`
   (GET отдаёт отфильтрованный список + полные счётчики по видам).
   Обзор для UI: GET `/api/memory/overview?sessionId=` — счётчики всех трёх слоёв.
8. **Cleanup.** Удаление сессии (DELETE /api/session/{id}) удаляет и файл
   рабочей памяти. Файлы-сироты `working/` подчищаются при старте
   `WorkingMemoryStore` (по отсутствию пары в `sessions/`).
9. **Старые сессии и записи без памяти.** Отсутствие файлов рабочей памяти —
   пустой слой (не ошибка). Файлы памяти читаются с `ignoreUnknownKeys`.
10. **Компрессия/ветки не задеты.** Слои памяти независимы от стратегий
    контекста: сводка/факты/ветки/окно работают как раньше. Переключение ветки
    НЕ меняет рабочую память (она сессионная, не веточная) — осознанно.

## Edge cases

- Пустая долговременная память у нового развертывания → блок памяти не
  инъецируется, инструменты возвращают понятные «пусто».
- Запрос агента `task_notes` при отсутствии сессии → инструмент отвечает
  ошибкой, не бросает исключение.
- Переполнение капов → инструмент возвращает `ok=false` с текстом «лимит …»;
  UI-форма показывает HTTP 400 текстом.
- Параллельные запросы к одной сессии → запись рабочей памяти под synchronized
  по файлу; upsert по id, последний побеждает.
- Удалённая сессия между GET и PUT рабочей памяти → 404.
- `memoryTools: false` при живых записях → блок памяти не инъецируется, панели
  доступны, инструменты модели не видны (не в specs()).

## Что не делаем (вне рамок)

- Векторные индексы и эмбеддинги — только детерминированный keyword-score.
- Автоматическая классификация/архивация долговременной памяти агентом.
- Память на уровне веток (рабочая память общая на сессию).
- Раздельные файлы долговременной памяти по видам — один файл с полем `kind`.
