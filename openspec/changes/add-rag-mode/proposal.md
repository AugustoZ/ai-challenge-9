# Change: RAG-режим «Штурмана» (add-rag-mode)

## Предусловие

- Индексер v1 не закоммичен — работы идут поверх рабочего дерева репо
  gw-club-indexer; пользователь коммитит вручную. Агент в обеих репо не коммитит.

## Зачем

«Штурман» отвечает на вопросы только из встроенных знаний модели: корпус
gw-club-docs (376 чанков, проиндексирован репо gw-club-indexer, стратегия
structure) в ход не вовлечён. Схема «вопрос → поиск релевантных чанков →
объединение с вопросом → запрос к LLM» сейчас невозможна: агент не видит
документы клуба и не может ссылаться на них. Нужны (а) RAG-режим с явным
управлением пользователем и (б) измерение его пользы — контрольный набор из
10 вопросов и автосравнение RAG vs no-RAG.

## Ключевые решения

1. **Интеграция с базой — HTTP-sidecar в репо индексера.** Подкоманда
   `gwclub serve` (новый модуль `serve.py`, только stdlib `http.server` —
   ноль новых зависимостей, порт по умолчанию 18700) отдаёт
   `POST /search` → `[{chunk_id, score, source, title, section, content}]`
   с ПОЛНЫМ content (сборка из SQLite row_map, а не snippet 200 символов).
   Preload индекса (config + embedder + FAISS + row_map) при старте, warm-up
   эмбеддинг-модели, `threading.Lock` вокруг embed+search. Sidecar запускается
   отдельно из корня репо индексера (относительный `index_dir`) и НЕ
   автостартуется Штурманом; существующее `search.py`/CLI индексера не
   меняется.
2. **Тумблер на панели.** «Поиск по базе (RAG)» в SettingsPanel — копия
   цикла `memoryTools` (default ВЫКЛ, персист в localStorage), передаётся как
   `ChatRequest.ragEnabled: Boolean?`.
3. **RAG активен только при** `body.ragEnabled == true` **И**
   `config.rag.url` сконфигурирован. `url == null` → обращения к sidecar нет,
   `retrievedSources=[]`.
4. **Пре-инжекция чанков в промпт ДО вызова LLM (не инструмент агента).**
   После обрезки семени (`trimmedSeed`) к семени цикла добавляется отдельное
   system-сообщение с RAG-блоком ПОСЛЕ блока памяти (последнее сообщение
   семени, 5-й хвостовой слот). Блок: заголовок-константа
   RAG_MARKER «РЕЛЕВАНТНЫЕ ДОКУМЕНТЫ», инструкция отвечать по приведённым
   документам и указывать источники в виде `[файл · раздел]`, нумерованные
   чанки `[N] source: <файл> · раздел: <section>` + полный текст чанка.
   Retrieval query = последнее user-сообщение (`body.message`; пустое —
   скип). Инжект НЕ в саб-вызовы (судья/экстрактор/суммаризатор) и НЕ до trim.
5. **Fail-open: сбой sidecar не роняет ход.** Недоступный адрес, таймаут,
   5xx или ошибка парсинга → ответ как обычно (HTTP 200), `retrievedSources=[]`,
   warn-лог (паттерн `runJudge`: runCatching + fold). Пустой результат поиска
   (0 чанков) — тоже без инжекта.
6. **Источники — метаданные, не полный content.** В ответе и в UI: chunkId,
   source, title, section, score, snippet (≤200 символов) — полный content в
   `RetrievedSource` не попадает (раздувал бы ответ и журнал).
   `ChatResponse.ragEnabled: Boolean` и `ChatResponse.retrievedSources:
   List<RetrievedSource>` всегда присутствуют в JSON (`@EncodeDefault(ALWAYS)`
   — серверный Json с `encodeDefaults=false`).
7. **UI.** Под ответом раскрывающийся блок «Источники» (клон JudgeReport:
   `<details>/<summary>`, амбер-summary, body в `--well`): строки
   `[N] source · section · score` (score в 3 знака) + бейдж-счётчик источников
   в шапке записи. Палитра не расширяется — только существующие токены
   tokens.css (стиль DESIGN.md).
8. **Конфиг-секция `rag`.** Поля: `url` (nullable), `k` (default 5),
   `timeoutMs` (default 10000), `maxBlockChars` (default 6000 — бюджет
   RAG-блока; пер-чанк обрезка с «…»). По доктрине конфигурации проекта
   (project.md): новые поля — nullable с default, старый `config.json` без
   секции `rag` обязан остаться рабочим. Env-переменных для rag-секции нет —
   только конфиг-файл.
9. **Измерение пользы — контрольный набор + харнесс.**
   `eval/rag-questions.yaml` — 10 контрольных вопросов по корпусу, у каждого
   ожидание (expectedSubstrings, 1–3 фрагмента, case-insensitive) и источники
   (expectedSources, 1–2 файла). `scripts/rag_eval.py` — харнесс сравнения:
   10 вопросов × 2 режима (rag off/on) через `POST /api/chat`, авто-проверки +
   баллы Судьи + токены/время, модель — обязательный CLI-параметр,
   markdown-отчёт-таблица 10×2 (`--out`), exit code всегда 0 (report-only).
10. **Детерминированный e2e.** Именованная константа
    `RagPrompts.RAG_MARKER = "РЕЛЕВАНТНЫЕ ДОКУМЕНТЫ"` в Kotlin + точная копия
    строки в `scripts/mock-llm.py` (паттерн FACTS_MARKER): mock при маркере в
    system-сообщениях отвечает детерминированным реплаем, цитирующим
    источники (refuse-режимы приоритетнее маркера).

## Граничные случаи

- Sidecar не запущен / порт закрыт / таймаут → fail-open: HTTP 200, обычный
  ответ, `retrievedSources=[]`, warn-лог.
- Sidecar вернул 0 чанков → RAG-блок в промпт не попадает, `retrievedSources=[]`.
- `ragEnabled=true`, но `config.rag.url` не сконфигурирован → обращения к
  sidecar нет, `retrievedSources=[]`, ответ как обычно.
- `ragEnabled=false` или поле отсутствует → ход байт-в-байт прежний (seed/
  trim/memory не меняются; весь прежний сюит зелёный без правок ассертов).
- Старый `config.json` без секции `rag` → валиден, дефолты (k=5,
  timeoutMs=10000, maxBlockChars=6000, url=null → RAG фактически выключен).
- Чанк содержит markdown/код-фенсы → структура RAG-блока не ломается
  (разметка блока без обратных кавычек и фенсов).
- Суммарный объём чанков превышает `maxBlockChars` → пер-чанк обрезка с
  «…», суммарный кап соблюдён.
- Судья и RAG одновременно → в семени оба блока, RAG-блок после памяти.
- Пустое user-сообщение → retrieval пропущен, RAG-блока нет.
- Sidecar обязан запускаться из корня репо индексера (относительный
  `index_dir`) — задокументированное условие.
- Параллельные запросы к sidecar → сериализованы lock'ом (ThreadingHTTPServer
  порождает поток на запрос; SentenceTransformer не потокобезопасен).

## Что не делаем (вне рамок)

- `search_docs`-инструмент агента, пороги релевантности, reranking,
  переформулировка запроса — нет.
- Интеграция с Mirror — нет.
- Env-переменные для rag-секции — нет (только конфиг-файл).
- Изменения `search.py`/`SearchResult`/хранилищ и существующего CLI-поведения
  индексера — нет (sidecar — новый модуль + однострочный wiring в cli.py).
- Новые зависимости в любой репо — нет (stdlib http.server; существующий
  ktor-client-cio; ktor-client-mock НЕ подключается — фейк через
  com.sun.net.httpserver).
- Автостарт sidecar из Штурмана, `/health` на sidecar — нет.
- Палитра не расширяется — только существующие CSS-токены.

## Отклонения от плана

Зарегистрированы при финализации (T12); детали в notepad-заметках волны.

1. **Контракт `rag/` (T4 → T6).** T4 реализовала `RagClient.search`,
   возвращающий `List<RetrievedSource>`: обрезка `content → snippet(200)`
   стояла внутри `KtorRagClient`, а `Passage` (полный content + метаданные)
   существовал только как входной тип `RagPrompts.buildRagBlock` и в тестах.
   План T6 требует полные тексты чанков в инжект-блоке → контракт расширен:
   `search`/`retrieve` возвращают `List<Passage>`, `RetrievedSource` для
   ответа строится через `Passage.toRetrievedSource()` (snippet =
   content.take(200); `SNIPPET_MAX_CHARS` перенесён в
   `RetrievedSource.companion`). `KtorRagClientTest`/`RagServiceTest`
   переведены на Passage-контракт, `RagPromptsTest` не тронут.
2. **Пример конфига (T3).** План: «закомментированный пример секции rag» в
   `config.example.json`. JSON не поддерживает комментарии, и тест
   «поставляемый пример конфига остаётся валидным для парсера» парсит файл
   строго, поэтому добавлена рабочая секция `rag` «как есть»
   (url `http://localhost:18700/search`), а не комментарий.
3. **Nosidecar-сценарий харнесса (T10).** Диагностика «sidecar не запущен»
   проверялась флагом `--rag-url` на закрытый порт (127.0.0.1:9), а не
   убийством живого sidecar: в момент верификации shared-стек
   (8099/18700/18080) принадлежал оркестратору, перезапускать его было
   запрещено.
4. **E2E на shared-стеке (T11).** E2E-смычка выполнялась на живом shared-
   стеке 8099/18700/18080 (nohup-паттерн): конфиг
   `/tmp/opencode/config.rag-smoke.json` = `config.dev.json` + секция `rag`
   (url → 18700) + порт 8099; приложение поднималось из него, sidecar и
   mock-llm уже работали и не перезапускались.
