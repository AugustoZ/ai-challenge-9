# AI Web Client (Kotlin + Ktor)

Проект на языке **Kotlin**, который отправляет запросы к AI API (OpenAI-совместимому) и выводит ответы в **веб-интерфейс**.

## Что делает проект

1. Запускает веб-сервер на **Ktor** (порт по умолчанию `8080`).
2. Отдаёт веб-интерфейс (React SPA) в браузере по адресу `/`.
3. По кнопке «Передать» фронтенд отправляет POST-запрос на наш сервер `POST /api/chat`.
4. Сервер обращается к внешнему AI API (Chat Completions), получает ответ и возвращает его браузеру.
5. Ответ отображается в чате.

## Структура проекта


## Настройка конфигурации

Конфигурация берётся из трёх источников, приоритет (от высшего к низшему):

1. **Переменные окружения** (`PORT`, `AI_API_URL`, `AI_API_KEY`, `AI_MODEL`, `CONFIG_FILE`)
2. **Конфиг-файл** (JSON, путь задаётся через `CONFIG_FILE`, по умолчанию `config.json`)
3. **Значения по умолчанию**

### Способ 1: конфиг-файл (рекомендуется)

Скопируйте пример и заполните своими значениями:

```bash
cp config.example.json config.json
```

Формат `config.json` (все поля опциональны):

```json
{
  "port": 8080,
  "apiUrl": "https://api.openai.com/v1/chat/completions",
  "apiKey": "ВАШ_API_КЛЮЧ",
  "model": "gpt-3.5-turbo"
}
```

Запуск с конфиг-файлом:

```bash
./gradlew run          # использует config.json из текущей директории
# или с указанием пути:
CONFIG_FILE=/path/to/config.json ./gradlew run
```

### Способ 2: переменные окружения

```bash
AI_API_KEY="ваш-ключ" ./gradlew run
```

### Используемые переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PORT` | Порт веб-сервера | `8080` |
| `AI_API_URL` | URL эндпоинта Chat Completions | `https://api.openai.com/v1/chat/completions` |
| `AI_API_KEY` | Ключ API | `ВАШ_API_КЛЮЧ` |
| `AI_MODEL` | Имя модели | `gpt-3.5-turbo` |
| `CONFIG_FILE` | Путь к JSON-конфигу | `config.json` |

### Секция `mcp`

Секция `mcp` конфиг-файла подключает внешние MCP-серверы (stdio-транспорт):
каждая запись — имя (`name`, уникально в пределах раздела), команда запуска
(`command`, обязательна — не может быть пустой), аргументы (`args`), переменные
окружения (`env`) и флаг `enabled` (`false` — сервер не запускается).
Отсутствие секции — MCP-серверы не подключены. В логах значения `env` не
печатаются (могут носить секреты).

```bash
# Терминал 1: бэкенд
```


## Способ рассуждения

Единственный способ обработки запроса — агентный цикл: модель работает с
инструментами (калькулятор, HTTP GET, текущие дата/время, песочница), разбивает
задачу на шаги и сама решает, когда ответ готов. Выбор режима удалён; поле
`reasoningMode` сервером больше не разбирается — устаревшее значение игнорируется
при десериализации без ошибки.

### Рассуждения (thinking)

Параметр «Рассуждения» на панели управляет передачей `thinking` в запрос к модели:

- **ВКЛ** — цепочка рассуждений модели активна: запросу добавляется `"thinking": {"type":"enabled"}`;
- **ВЫКЛ** — рассуждения выключены: `"thinking": {"type":"disabled"}`.

На бэкенде параметр `thinkingEnabled` в `ChatRequest` необязателен: если он `null` — поле `thinking` в запрос к модели не попадает вовсе.

### Учёт лимита токенов

Параметр «Топливо» (круглая шкала на панели; внутренне — `max_tokens`) трактуется как
бюджет **всего видимого ответа** и работает на двух уровнях:

1. Передаётся в API как `max_tokens`;
2. Дополнительно указывается модели в системной инструкции — она планирует объём
   и не обрывает ответ на середине (это работает даже если API игнорирует `max_tokens`).

Лимит действует на каждый вызов модели в агентном цикле (шаг с инструментами,
принудительный финал по гварду); токены в метаданных ответа суммируются по всем
вызовам.

### Выбор модели и провайдера

В разделе «Параметры модели» панели есть селект **«Модель»**: модели сгруппированы
по провайдерам. Сервер получает списки от каждого провайдера (`GET /api/models`);
выбранная пара «провайдер + модель» передаётся в каждом запросе
(`ChatRequest.provider` + `ChatRequest.model`), выбор сохраняется в localStorage.

### Провайдеры LLM

Провайдеры настраиваются в `config.json`. Поля верхнего уровня `apiUrl`/`apiKey`/`model`
задают **провайдер по умолчанию** (OpenAI-совместимый); массив `providers` добавляет
дополнительных. Поддерживаются два протокола:

| `type` | Протокол | Пример |
|---|---|---|
| `openai` (по умолчанию) | OpenAI-совместимый Chat Completions (`{base}/chat/completions`, список — `{base}/models`) | OpenAI, vLLM/GPUStack, LocalAI, Ollama-шлюзы |
| `opencode` | API локального экземпляра OpenCode: модели — `GET /api/model`, генерация — сессии `POST /session` → `POST /session/{id}/message` (на серверах v2 сначала пробуется одноразовый `POST /api/generate`) | `opencode serve` с бесплатными моделями |

```json
{
  "apiUrl": "https://gpustack.example/v1/chat/completions",
  "apiKey": "...",
  "model": "deepseek-v4-flash",
  "allowedModels": ["deepseek-v4-flash", "glm-5.3-flash", "qwen3.8-27b"],
  "providers": [
    {
      "id": "opencode",
      "name": "OpenCode (бесплатные)",
      "type": "opencode",
      "apiUrl": "http://localhost:4096",
      "apiKey": "пароль_сервера_opencode",
      "upstream": "opencode",
      "models": ["big-pickle", "nemotron-3.5-lightning-free"]
    }
  ]
}
```

- `allowedModels` — белый список моделей провайдера по умолчанию (порядок сохраняется);
  остальные провайдеры показывают список из своего `models` (явный список) или от API.
- `apiKey` провайдера `opencode` — пароль сервера (задаётся при запуске
  `OPENCODE_SERVER_PASSWORD=... opencode serve --port 4096`; имя пользователя — `opencode`).
- `upstream` — id провайдера внутри OpenCode для адресации модели (например, `opencode`
  для бесплатных моделей zen).
- **Бесплатные модели OpenCode zen** требуют zen-ключ (OpenCode Console → API keys).
  Шлюз подключается как обычный `openai`-провайдер с `apiUrl: "https://opencode.ai/zen/v1/chat/completions"`.
  Нюансы бесплатного тарифа: лимит запросов (ошибка `429 FreeUsageLimitError` — подождать
  и повторить), часть моделей закрыта геоблокировкой (`403 RegionError`), отдельные
  модели могут быть недоступны на upstream (`400 server_error`).
- **Альтернатива — локальный экземпляр OpenCode**: провайдер типа `opencode` с `apiUrl`,
  указывающим на КОРЕНЬ сервера (например, `http://localhost:4096`; запуск —
  `OPENCODE_SERVER_PASSWORD=... opencode serve --port 4096`, apiKey — пароль сервера).
  Важно: apiUrl у провайдера `opencode` — это корень сервера, а не endpoint
  chat/completions; запросы идут на сессии `POST /session → POST /session/{id}/message`.
- OpenCode — агент, а не сырой API: каждый запрос проходит цикл агента, поэтому время
  ответа больше, а токены включают его системный контекст. Параметры генерации
  (temperature, max_tokens, стоп-фраза, рассуждения) протоколом OpenCode не передаются.

### Замер скорости

Каждый ответ фиксирует приборные показания (в шапке записи журнала):

- **время** — полное время обработки на сервере (все вызовы LLM), `ChatResponse.elapsedMs`;
- **скорость** — токенов в секунду (completionTokens / время);
- **топливо** — токены запрос/ответ/всего, как раньше.

### Режим Судья

Тумблер **«Судья»** (раздел «Приёмка») включает контрольную проверку: после получения
ответа сервер отдельным вызовом LLM оценивает его по четырём критериям — корректность
фактов, качество ответа, скорость (по замерам времени и токенов/с) и ресурсоёмкость
(оправданы ли потраченные токены). Каждый критерий получает балл 1–10 с комментарием,
итоговый балл и вердикт; заключение раскрывается под ответом (свернуть/развернуть).
Срыв проверки не роняет основной ответ — вместо баллов покажут причину.

## Пользователи и персонализация

«Штурман» — многопользовательский: у каждого пользователя свой ПИН и свои данные
(сессии, рабочая память, долговременная память, предпочтения, журнал обменов).
Авторизация и изоляция — на сервере; фронтенд хранит токен в `sessionStorage`.

### Вход по ПИН и создание пользователя

- **Создание** (`POST /api/auth/users`, открытый роут): тело `{name, pin}` — имя
  1..25 символов (буквы, цифры, спецсимволы; без управляющих; дубликаты имён
  разрешены — пользователей различают ПИНЫ), ПИН ровно 4 цифры. Ответ —
  `UserCreatedResponse` с токеном: создание сразу является авто-входом.
- **Вход** (`POST /api/auth/login`, открытый роут): тело `{userId, pin}`. Ответ —
  `AuthTokenResponse` с токеном. Неверный ПИН или пользователь — `401`
  «Неверный ПИН или пользователь» (ответ не раскрывает, существует ли пользователь:
  неудачи неизвестных id тоже учитываются в счётчике).
- **Список пользователей** (`GET /api/auth/users`, открытый роут): для экрана входа,
  только `id` + `name` — хеши и ПИНы наружу не идут.
- **Удаление** (`DELETE /api/auth/users/{id}`, защищённый роут): каскадное удаление
  данных пользователя (сессии с рабочей памятью, предпочтения, каталог
  долговременной памяти, токены) — `204`. Единственный оставшийся пользователь не
  удаляется — `400` «Нельзя удалить единственного пользователя»; неизвестный id —
  `404` «Пользователь не найден.».

ПИН хранится только как `SHA-256(salt + pin)` (соль — 16 байт `SecureRandom`),
сравнение — constant-time (`MessageDigest.isEqual`). Файл пользователя —
`<dataDir>/users/{userId}.json`.

**Защита от подбора**: 3 неудачные попытки подряд (счётчик на пользователя, в
памяти) → кулдаун 30 секунд, в течение которого не проходит даже верный ПИН
(`429`, текст «Слишком много неудачных попыток входа. Повторите через N сек.»).
Успешный вход обнуляет счётчик; отсиженный кулдаун — тоже.

### Токен авторизации

Токен передаётся в заголовке **`X-Auth-Token`** на **всех** запросах, включая SSE
(`POST /api/chat/stream`). Токен — 32 случайных байта `SecureRandom` (Base64URL,
256 бит) и живёт **только в памяти процесса**:

- **рестарт сервера = re-login**: токены не персистируются на диск, JWT/refresh
  нет (guardrail проекта);
- проверка токена — в **едином центральном choke point**: `intercept` в начале
  `aiRoutes` (см. `routes/Routes.kt`). Всё под `/api/*`, кроме открытого
  whitelist'а (`POST /api/auth/login`, `GET`/`POST /api/auth/users`) и статики,
  без валидного токена получает `401 {"error":"Требуется вход"}`. Токен не
  проверяется ни в одном route-блоке; владелец кладётся в атрибут вызова
  `UserIdKey`, который потребляют роуты.

На фронтенде токен хранится в `sessionStorage` (ключ `shturman.auth.v1`): вкладки
браузера независимы друг от друга; любой `401` разлогинивает приложение в экран
входа; рестарт бэкенда инвалидирует токен (вход заново).

### Предпочтения (опросник из 7 вопросов)

Предпочтения применяются **серверно к каждому LLM-запросу** (домен `prefs/`):

- `GET /api/preferences` — предпочтения текущего пользователя; файла ещё нет —
  дефолтные значения (`ты`/`дружелюбный`/`Русский`/`текст`/`средне`/пустые),
  а не 404 (прерванный визард — обычное состояние);
- `PUT /api/preferences` — сохранение: серверная валидация (словари обращения/тона/
  языка/длины; лимиты 255/1000/1000 на свободные поля), нарушение — `400` с русским
  текстом, называющим поле; ответ — сохранённый (санитизированный) объект. Контракт —
  замещение: частичный JSON дополняется дефолтами для отсутствующих полей.
- Поля: `addressForm` (ты/вы/пилот/гонщик), `tone` (формальный/дружелюбный/
  панибратский/роботизированный), `language` (Русский/Английский — интерфейс
  остаётся русским), `answerStructure` (таблицы/текст/стихи либо описание ≤255),
  `length` (кратко/средне/развернуто — **текстовая инструкция** модели с ориентиром
  ~1k/3k/10k токенов; слайдер «Топливо» остаётся отдельным жёстким капом),
  `avoidTopics` ≤1000, `interests` ≤1000.

Блок «Предпочтения пользователя» (≤2500 символов) инжектится хвостовым
system-сообщением **в единой точке** — в `handleAgent`, после `SessionHistory.trim`,
перед блоком памяти; инъекция безусловна (нет файла — блок дефолтов), поэтому
покрывает прямой, пошаговый (рассуждения) и стриминговый режимы. Саб-вызовы
(судья, экстрактор фактов, суммаризатор) строят свои промпты вне seed и блок не
получают. Концепт назван «Предпочтения»/preferences — не «profile» (имя занято
видом долговременной памяти).

### Изоляция данных

Изоляция **полная** и выполняется на уровне хранилищ:

| Данные | Раскладка per-user |
|---|---|
| Сессии | `Session.userId`; `<dataDir>/sessions/{id}.json` (legacy без владельца — `userId: null`) |
| Рабочая память | `<dataDir>/working/{sessionId}.json` (файл на сессию — значит и на пользователя) |
| Долговременная память | `<dataDir>/memory/{userId}/longterm.json` (кап 200 записей на пользователя) |
| Предпочтения | `<dataDir>/preferences/{userId}.json` |
| Журнал обменов (`GET /api/log`) | записи помечены `userId`; фильтр отдаёт только свои (записи без владельца не видны никому) |

**Кросс-доступ к чужим ресурсам — `404`, а не `403`**: существование чужих данных не
раскрывается — в том числе `DELETE /api/memory/{id}` чужой/неизвестной записи
отвечает `404` «Запись не найдена.» (до переключения на per-user раскладку повторное
удаление отвечало `{"deleted":false}`).

**Задокументированные ограничения**:

- эвикция `MAX_SESSIONS = 50` **глобальная** (по старости на всё хранилище), per-user
  квот нет;
- `GET /api/files/{name}` — **общая песочница**: файлы, записанные агентом, видны
  любому вошедшему пользователю (auth-гейт, но без привязки к владельцу);
- рестарт процесса = re-login (токены в памяти);
- долговременные записи вида `profile` **не** мигрируют в опросник — остаются памятью.

### Миграция «Шумахер» (первый старт на legacy-данных)

При старте приложения, **до построения маршрутов**, выполняется идемпотентная
миграция (`auth/ShturmanMigration.kt`): если пользователя «Шумахер» нет, а
legacy-артефакты есть (сессии без владельца или общий файл `memory/longterm.json`),
создаётся пользователь «Шумахер», наследующий все до-авторизационные данные:

- случайный 4-значный PIN печатается в **stdout ровно один раз** (повторно сообщение
  не появится) в формате константы `ShturmanMigration.PIN_LINE_FORMAT`:

  > `МИГРАЦИЯ: создан пользователь «Шумахер» для унаследованных данных. PIN: %s — запишите его, это сообщение больше не появится.`

- файлы осиротевших сессий переписываются с `userId` «Шумахера» (атомарно,
  tmp + rename);
- `memory/longterm.json` переносится в `memory/{userId}/longterm.json` (atomic move;
  существующий целевой файл не перезаписывается — при сбое legacy-файл остаётся на
  месте, предупреждение в `stderr`, данные не теряются).

Второй старт — no-op: у всех сессий есть владелец, файл памяти переехал, «Шумахер»
существует. Это же защищает от ре-миграции после удаления пользователей: каскад
удаления убирает и сессии, и каталог памяти, осиротевших артефактов не остаётся.

## Память агента

У агента три слоя памяти. Кнопка **«Память»** в верхней полосе (рядом с «Топливо за сессию») открывает панель с тремя вкладками:

| Слой | Что хранит | Живёт |
|---|---|---|
| **Краткосрочная** | Текущий диалог: счётчик ходов и признак сводки | Пока жива сессия |
| **Рабочая** | Заметки по текущей задаче (свои и агента) | Пока жива сессия (файл на диске переживает перезапуск сервера) |
| **Долговременная** | Профиль пользователя, принятые решения, накопленные знания | Общая для сессий пользователя (изоляция per-user, см. «Пользователи и персонализация») |

### Управление памятью

- **Рабочая** и **Долговременная** вкладки позволяют добавить запись вручную (заголовок + текст), отредактировать и удалить любую запись; рабочая очищается целиком кнопкой «Очистить». В долговременных записях виден вид (Профиль / Решение / Знание) и источник (бейдж «агент» или «вы»).
- **Краткосрочная** вкладка показывает сводку по текущему диалогу (ходы, сводка).

### Инструменты памяти агента

Тумблер **«Инструменты памяти агента»** (секция «Память» панели, по умолчанию ВКЛ) управляет доступом агента к памяти:

- **ВКЛ** — агент видит три инструмента и получает блок памяти в контекст: `task_notes` (рабочая память — сохраняет шаги и находки свободно), `memory_save` и `memory_recall` (долговременная память — **только по явной просьбе** пользователя: «запомни», «сохрани»).
- **ВЫКЛ** — агент не видит инструменты памяти и блок памяти; запрос уходит с `"memoryTools":false`, панель работает как раньше (ручное управление доступно всегда).

### Хранение и лимиты

- Рабочая память — `<dataDir>/working/<sessionId>.json` (по файлу на сессию), долговременная — `<dataDir>/memory/{userId}/longterm.json` (файл на пользователя; общая раскладка `memory/longterm.json` остаётся только legacy-дефолтом и через API не видна). Запись атомарная (через tmp-файл).
- Капы: рабочая — до **24** записей на сессию (заголовок ≤ 120, текст ≤ 4000 символов); долговременная — до **200** записей на пользователя (заголовок ≤ 120, текст ≤ 2000 символов, до 8 тегов по 24 символа).

### Эндпоинты

- `GET/PUT/DELETE /api/session/{id}/working` — заметки рабочей памяти сессии (PUT — добавить/заменить, DELETE — очистить; удаление одной — `DELETE .../working/{entryId}`);
- `GET /api/memory?kind=&q=` — долговременные записи текущего пользователя + счётчики по видам; `POST /api/memory` — новая запись (источник «user»); `PUT/DELETE /api/memory/{id}` — правка/удаление (запись не найдена или чужая — `404` «Запись не найдена.», существование чужих данных не раскрывается);
- `GET /api/memory/overview?sessionId=` — сводка всех трёх слоёв для панели памяти.

### Развитие памяти

Хранение и поиск долговременной памяти вынесены за порты `MemoryRepository` и `MemorySearchEngine` — план развития выглядит так:

| Стадия | Что появляется |
|---|---|
| **0 (сейчас)** | Порты + keyword-поиск |
| **1** | SQLite-репозиторий + полнотекстовый поиск FTS5 |
| **2** | Векторный поиск (эмбеддинги) + гибрид |

Инструменты агента и HTTP-роуты работают только с портами, поэтому замена бэкенда (файловый JSON → SQLite → векторное хранилище) не требует переписывания самой фичи. Контрактный тест-набор (`MemoryRepositoryContractTest`) гарантирует, что любая новая реализация ведёт себя так же, как текущая. Выбор реализации поиска задаётся полем `memory.search` в конфиге (пока поддерживается только `"keyword"`, значение по умолчанию).

## Компрессия истории

В одиночных режимах (`default`/`direct`/`step_by_step`/`agent`) сервер отдаёт модели всю историю сессии, и `prompt_tokens` растут с каждым сообщением. Компрессия укорачивает контекст: последние 5 сообщений уходят в запрос «как есть», более старая история сворачивается в сводку (rolling summary). Сводка хранится **отдельно** в JSON сессии (поле `summary`) и подставляется в запрос как `system`-сообщение вместо полного перечня сообщений.

### Как работает

- **Окно.** Последние `compressionWindowSize` (default 5) сообщений истории уходят в запрос без изменений. Если граница окна наезжает на `role="tool"`, окно расширяется назад до ближайшего `user`-сообщения — пара `assistant(tool_calls) → role="tool"` не рвётся. Стратегия **деструктивна**: после каждого успешного обмена хранилище сессии физически урезается до последних `compressionWindowSize` сообщений — всё за окном отбрасывается безвозвратно.
- **Сводка.** Когда вне окна накопилось `compressionMergeEvery` (default 5) сообщений, выполняется **один** merge: все накопившиеся внеоконные сообщения сдаются суммаризатору (тот же провайдер, отдельный вызов), и результат дописывается к существующей сводке. Слитые сообщения **удаляются из истории** (consume-and-store), так что `prompt_tokens` сжатой стороны реально падают.
- **Бюджет сводки.** `compressionSummaryMaxTokens` (default 400) токенов. Если сводка длиннее: один повторный вызов с инструкцией «сожми жёстче», при повторном превышении — жёсткая обрезка по границе предложений.
- **Сбой суммаризатора не роняет чат.** Ошибка вызова ловится `runCatching`: сохраняется прежняя сводка, ответ возвращается как обычно, `summaryTokens = null`.

### Настройки

Все четыре поля задаются **только в конфиг-файле** — переменных окружения для компрессии нет (решение задачи 2: `System.getenv` в JVM не подменяется в тестах):

| Поле | По умолчанию | Описание |
|---|---|---|
| `compressionEnabled` | `false` | Сжимать историю по умолчанию (поле запроса перекрывает это значение) |
| `compressionWindowSize` | `5` | Сколько последних сообщений уходит в запрос «как есть» (≥ 1); при стратегии «Окно» — также размер хранилища после каждого обмена (за окном отбрасывается) |
| `compressionMergeEvery` | `5` | Сколько сообщений вне окна запускает один merge (≥ 1) |
| `compressionSummaryMaxTokens` | `400` | Бюджет сводки в токенах (≥ 50) |

Нарушение ограничений (`windowSize`/`mergeEvery` < 1, `summaryMaxTokens` < 50) роняет старт сервера с внятным сообщением.

### Поля запроса и ответа

- `ChatRequest.compressionEnabled` (опционально, `Boolean?`): флаг сжатия **на конкретный запрос**. Приоритет: **поле запроса > конфиг** — `null` в запросе берёт значение из `compressionEnabled` конфига.
- `ChatResponse.summaryTokens` (`Int?`): токены вызова суммаризатора. Заполняется **только когда merge реально выполнился** за этот запрос; иначе `null`. Ключ при этом всегда присутствует в JSON.
- `ChatResponse.summaryApplied` (`Boolean`): подставлена ли сводка в контекст этого запроса. Всегда присутствует в JSON.

### Режим сравнения (зеркальный)

Тумблер **«Режим сравнения»** (секция «Память» панели) прогоняет каждый запрос параллельно через две twin-сессии — без сжатия и со сжатием — и показывает ответы с расходом бок о бок:

1. Откройте панель приборов, секция «Память», включите «Режим сравнения».
2. Отправьте сообщение: уходят два параллельных `POST /api/chat/stream` в собственные twin-сессии (id выдаёт сервер), в основной журнал и счётчик «Топливо за сессию» ничего не пишется.
3. Под журналом появляется блок сравнения: две колонки «Без сжатия» и «Со сжатием», в каждой — ответ, строка топлива и (на сжатой стороне, когда сводка применена) бейдж «Сводка применена».
4. Итоговая строка: `Без сжатия: N ток · Со сжатия: M ток (из них сводка: K) · экономия: X%`. Токен, которого провайдер не отдал (usage `null`), показывается как «н/д» — не 0 и не NaN.

Выключение тумблера завершает сравнение и сбрасывает накопленные показания; сами twin-сессии остаются в перечне `/api/sessions` как обычные. Качество ответа не оценивается автоматически — вы смотрите на два ответа и расход сами (LLM-as-judge в сравнение не встроен).

## Стратегии управления контекстом

Старый тумблер «Сжатие истории» обобщён в единый переключатель из пяти позиций: **Выкл / Окно / Сводка / Факты / Ветки**. Стратегия определяет, как формируется контекст запроса: что уходит модели, а что остаётся только в хранилище. Стратегии действуют на каждый запрос: обработка ведётся агентным циклом с памятью сессии (сессия создаётся на каждый запрос).

### Пять стратегий

| Стратегия | Значение `contextStrategy` | Что уходит в контекст |
|---|---|---|
| Выкл | `off` | Полная история с действующими капами (`trim`/`trimContext`), без компрессии |
| Окно | `window` | Последние 5 сообщений (`compressionWindowSize`) «как есть». Деструктивная: после каждого ответа хранилище урезается до последних 5 сообщений, за окном отброшено безвозвратно; накопленная сводка не подставляется |
| Сводка | `summary` | Rolling summary более старшей истории + окно (consume-and-store: слитые сообщения удаляются из истории) — поведение «Сжатия истории», сохранено байт-в-байт |
| Факты | `facts` | KV-блок фактов диалога (system-сообщение «ключ: значение») + последние 3 сообщения. Non-destructive view |
| Ветки | `branching` | Полная история активной ветки (как «Выкл») + капы. Ручные развилки по кнопке «+ Развилка» — чекпоинт активного состояния в новую ветку; лимит 8 снимков-веток на сессию. Авто-форк удалён: ветки создаёт только пользователь |

### Переключатель и приоритет

Стратегия разрешается на каждый запрос в порядке убывания приоритета:

1. **Поле запроса `contextStrategy`** — валидное значение всегда выигрывает;
2. **Legacy-флаг `compressionEnabled`** (поле запроса или конфиг) — когда стратегии нет: `true` → Сводка, `false` → Выкл;
3. **Ключ конфига `contextStrategy`** — когда выше нет ни явной стратегии, ни legacy-флага.

Неизвестный `contextStrategy` (вне `off`/`window`/`summary`/`facts`/`branching`) — HTTP 400 с текстом, называющим неизвестный id и допустимый набор. Запрос не обрабатывается, сессия не меняется.

**Важно: история после «Сводки» и «Окна» невосстановима.** Деструктивных стратегий две, с разной механикой: **«Сводка»** сливает сообщения за окном в сводку и удаляет их из истории (consume-and-store); **«Окно»** после каждого успешного обмена физически урезает хранилище до последних `compressionWindowSize` (default 5) сообщений — всё за окном отбрасывается безвозвратно. После использования «Сводки» или «Окна» удалённая история невосстановима — при переключении на недеструктивные стратегии (Выкл / Факты / Ветки) вернётся только текущее окно/история, а накопленная сводка игнорируется (в запрос не подставляется).

### Зеркало: стратегия на колонку

«Режим сравнения» обобщён до «стратегия на колонку»: каждая колонка получает свою стратегию из селекта в шапке колонки — **Выкл / Окно / Сводка / Факты** («Ветки» в колонках недоступно). Заголовки колонок показывают выбранные стратегии (labels меняются при смене выбора). Payload каждой стороны: базовый payload + собственный `sessionId` + `judgeEnabled=false` + `contextStrategy` стратегии колонки; поле `compressionEnabled` в per-side payload не передаётся. Twin-сессии никогда не получают стратегию «Ветки»: ветвление в зеркале недоступно, панель веток скрыта. Метрики (токены, бейдж «Сводка применена», статус сводки) — по каждой колонке.

### Ветки: эндпоинты и поля

- `GET /api/session/{id}/branches` — плоский список веток сессии: первая запись — живое активное состояние, далее снимки веток. Поля записи: `branchId` (`null` — исходная история до первого форка), `label` (корень — «Основная», ветки — «Ветка N»), `forkUserCount`, `userCountSinceFork`, `messageCount`, `active` (ровно одна запись — `true`).
- `POST /api/session/{id}/branches` — **ручная развилка** (чекпоинт по кнопке «+ Развилка»): снимок текущего активного состояния в новую ветку-близнец «Ветка N», тело запроса не нужно. Активная ветка не меняется — один клик создаёт одну ветку, развилок можно завести несколько и переключаться между ними для параллельных диалогов. Ответ — запись созданной ветки (форма списка выше, `active=false`); неизвестная сессия — 404, достигнут лимит 8 веток — 409.
- `POST /api/session/{id}/branches/activate` (тело `{"branchId":"…"}`) — своп активного состояния с снимком выбранной ветки (своп без потерь: прежнее активное состояние сохраняется новой веткой).
- `ChatRequest.branchId` — если указано и не совпадает с активной веткой, сервер активирует эту ветку **до** обработки запроса; `null` — активная ветка.
- `ChatResponse.contextStrategy` — разрешённая для запроса стратегия (echo, ключ всегда в JSON).
- `ChatResponse.branchId` — id активной ветки после обработки (`null` — исходная история, без ветки).
- `ChatResponse.facts` — актуальный список фактов сессии (массив `{key, value}`, пустой, если фактов нет); экстракция — после ответа ассистента и только при стратегии «Факты».

### Настройки

Поле задаётся **только в конфиг-файле** — переменных окружения для него нет:

| Поле | По умолчанию | Описание |
|---|---|---|
| `contextStrategy` | `off` | Стратегия по умолчанию, когда запрос не несёт ни явной стратегии, ни legacy-флага (нижний уровень приоритета) |

## Пример использования API напрямую

Все защищённые роуты требуют токен в заголовке `X-Auth-Token` (исключение —
открытые auth-роуты и статика). Сначала создайте пользователя или войдите и
возьмите токен:

```bash
# Создать пользователя и сразу получить токен (авто-вход)
curl -s -X POST http://localhost:8080/api/auth/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Пилот","pin":"0407"}'
# → {"token":"...","user":{"id":"...","name":"Пилот"}}

# ...или войти по ПИН (userId взять из GET /api/auth/users)
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"userId":"<id>","pin":"0407"}'
# → {"token":"...","user":{"id":"...","name":"Пилот"}}
```

Далее — токен в заголовке каждого запроса:

```bash
curl -s -X POST http://localhost:8080/api/chat \
  -H "Content-Type: application/json" \
  -H "X-Auth-Token: <ВАШ_ТОКЕН>" \
  -d '{"message":"Привет, как дела?","thinkingEnabled":false,"judgeEnabled":true,"provider":"default","model":"deepseek-v4-flash"}'
```

Список моделей по провайдерам: `curl -H "X-Auth-Token: <ВАШ_ТОКЕН>" http://localhost:8080/api/models`

Без токена защищённый роут отвечает `401 {"error":"Требуется вход"}`.
