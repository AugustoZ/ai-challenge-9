# gwclub-indexer

Конвейер индексации и векторного поиска по русскоязычным документам корпуса
`gw-club-docs` (FAQ, руководства прошивок/установки и т.д.).

Ключевая идея — сравнить **две стратегии разбиения текста на чанки** на
детерминированном эталоне: `fixed` (нарезка по токенам с перекрытием) и
`structure` (разбиение по markdown-заголовкам с пробросом заголовочного
трейла). Обе стратегии эмбеддятся моделью E5 и складываются в FAISS + SQLite,
после чего результаты сравниваются метриками поиска.

Примечание (10.10.2026): гигантские markdown-таблицы (например, таблица
контактов «- РФ -» на ~6k токенов) больше не остаются одним overflow-чанком —
`structure` режет их пачками строк ≤ `max_tokens`, каждая пачка повторяет
шапку таблицы, чтобы отдельные строки (город → контакты) оставались
находимыми векторным поиском. После правки — `uv run gwclub index --strategy structure`.

## Назначение

1. **Chunking**: тексты из `docs_root` делятся на чанки двумя стратегиями.
2. **Embeddings**: каждый чанк эмбеддится локальной моделью
   `intfloat/multilingual-e5-small` (dim 384), с E5-префиксами `query:`/`passage:`.
3. **Хранение**: FAISS-индекс векторов (+ SQLite с метаданными) на стратегию.
4. **Поиск**: косинусная близость без ре-ранкинга и без BM25 (чисто вектор).
5. **Eval**: детерминированное сравнение стратегий по метрикам Recall@5 / MRR@10.

## Quickstart

```bash
# 1. Установка (статически объявленные зависимости, включая dev-инструменты).
uv sync --all-extras

# 2. Генерация детерминированного эталона (без LLM).
uv run gwclub groundtruth

# 3. Индексация обеими стратегиями.
uv run gwclub index --strategy both

# 4. Пример поиска по структурированному индексу.
uv run gwclub search --strategy structure -k 5 "вопрос"

# 5. Сравнение стратегий -> reports/comparison.md + reports/eval-results.json.
uv run gwclub eval
```

> **Первый запуск** `index`/`eval`/`search` скачивает модель E5 (~470 МБ) с
> HuggingFace Hub. После того как модель закэширована локально, всё работает
> офлайн. Если модель недоступна, используйте `--config` с
> `embedding.provider = "openai_compat"` либо продуктовый эмбеддер (см. ниже).

Полный список команд: `gwclub --help`.

## Схема метаданных

### chunk_id

Детерминированный идентификатор чанка — первые 16 hex-символов SHA-256 от
`source | strategy | chunk_index`:

```
chunk_id = sha256(f"{source}|{strategy}|{chunk_index}")[:16]
```

Одинаковые входы всегда дают одинаковый `chunk_id`; повторная индексация
воспроизводит тот же набор (детерминизм проверен в tests).

### Таблица `chunks` (SQLite, на файл `index-{strategy}.sqlite`)

| Поле | Тип | Смысл |
|---|---|---|
| `chunk_id` | TEXT PK | Идентификатор чанка (см. выше). |
| `source` | TEXT | Относительный путь документа (напр. `ru/FAQ-all.md`). |
| `title` | TEXT | Заголовок H1 документа. |
| `section` | TEXT | Заголовочный трейл (`A > B > C`), либо `(документ)` для fixed-чанков. |
| `locale` | TEXT | Локаль документа. |
| `chunk_index` | INTEGER | Порядковый индекс чанка внутри документа данной стратегии. |
| `strategy` | TEXT | `fixed` или `structure`. |
| `token_count` | INTEGER | Число токенов в `content`. |
| `char_count` | INTEGER | Число символов в `content`. |
| `content` | TEXT | Полный текст чанка. |
| `faiss_row` | INTEGER | Позиция вектора в FAISS-индексе (см. ниже). |

### Таблица `index_meta` (ключ-значение)

Ключи:

- `embedding_model` — имя модели (напр. `intfloat/multilingual-e5-small`).
- `dim` — размерность эмбеддинга (для E5 — `384`).
- `prefix_mode` — стиль E5-префиксов (`e5` для локального эмбеддера,
  `none` для mock в тестах).
- `strategy` — стратегия, которой построен индекс.
- `params_json` — JSON-сериализованные параметры chunking (для `structure`
  добавляются `merge_short_sections` / `min_section_tokens`).
- `built_at` — момент построения (информационно).

### faiss_row

`faiss_row` — это позиция вектора чанка в FAISS-индексе (номер строки, по
которому `index.search` возвращает top-k). Она присваивается при построении
как порядковый номер в списке чанков. Поиск по векторам возвращает
`faiss_row` → JOIN к `chunks` через `faiss_row` даёт метаданные результата.

## Конфиг (`config.toml`)

Опциональный override-файл в корне проекта; при отсутствии используются
дефолты из `config.py`. Секции и ключевые параметры (дефолты в скобках):

**`[paths]`**

- `docs_root` — корень корпуса (`/Users/augustoz/AI Advent Challenge 9/gw-club-docs`).
- `index_dir` — каталог индексов (`data/index`).
- `groundtruth_file` — путь к эталону (`eval/groundtruth.yaml`).
- `reports_dir` — каталог отчётов (`reports`).

**`[filters]`**

- `exclude_paths` — список файлов, исключаемых из индексации
  (`ru/test.md`, `ru/test-page.md`, `ru/test_haval_table.md`, `ru/Test-install.md`).
- `exclude_draft` — пропускать draft-документы (`true`).
- `min_chars` — минимальная длина документа (`60`).

**`[chunking.fixed]`**

- `max_tokens` — максимальный размер чанка (`400`).
- `overlap_tokens` — перекрытие между чанками (`60`).

**`[chunking.structure]`**

- `max_tokens` / `overlap_tokens` — то же, что у fixed (`400` / `60`).
- `merge_short_sections` — склеивать короткие секции с предыдущим чанком (`true`).
- `min_section_tokens` — порог «короткой» секции (`40`).

**`[embedding]`**

- `provider` — `local` (E5, локально) или `openai_compat` (`local`).
- `model` — имя модели (`intfloat/multilingual-e5-small`).
- `device` — `auto` / `mps` / `cpu` (`auto`).
- `[embedding.openai_compat]` — `base_url`, `api_key_env`, `model`
  (для внешнего OpenAI-совместимого сервера).

**`[search]`**

- `default_strategy` — стратегия поиска по умолчанию (`structure`).

## Как читать `reports/comparison.md`

Порядок секций нормативный: **Правило победителя** идёт строго **до** таблицы
метрик, чтобы читатель знал, как судить, раньше, чем увидит цифры.

- **Правило победителя**: `structure` выигрывает, если
  `Recall@5(structure) − Recall@5(fixed) ≥ 5 п.п.`; при разнице меньше 5 п.п.
  сравнивается `MRR@10`; при равенстве MRR — паритет и дефолт `search =
  structure`.
- **Recall@5** — доля релевантных чанков, попавших в top5 (в среднем по
  эталонам).
- **MRR@10** — средний `1/ранг` первого релевантного чанка в top10 (0, если
  нет). При равенстве Recall именно MRR разрешает спор.
- **coherence** — прокси-метрика внутренней согласованности чанков
  (интра-похожесть предложений против похожести с соседним чанком). Это не
  качество ответа, а ориентир.
- **Распределение длин** (p50/p90/max/%<30/%>max) — показывает, насколько
  стратегия режет длинные разделы и сколько мелких пыльных чанков даёт.

**Оговорки**:

1. **Heading-as-query тривиально благоприятствует `structure`** — эталонный
   запрос равен дословному заголовку, а структурные чанки несут заголовок.
   В текущем эталоне **0 heading / 30 faq**, т.е. этого смещения сейчас нет.
2. **FAQ-вопросы — честный тест**: это человеческие вопросы, не оформленные
   как заголовки; они не дают `structure` преимущества по форме.
3. **coherence — прокси**, не истина.

## Как добавить эталоны вручную

Отредактируйте `eval/groundtruth.yaml` (поддерживается YAML-список объектов).
Формат полей:

```yaml
- query: "Как отформатировать флешку?"
  source: "ru/FAQ-all.md"
  section: "1. Подготовка флешки > Как правильно отформатировать флешку?"
  origin: "faq"
```

- `query` — текст запроса.
- `source` — относительный путь документа.
- `section` — заголовочный трейл эталона (для `faq` — как в документе).
- `origin` — `heading` (заголовок, переиспользованный как запрос) или
  `faq` (человеческий вопрос); иное значение — ошибка при загрузке.

`gwclub eval` читает файл как есть: просто пересохраните его (или добавьте
строки) и запустите `uv run gwclub eval` — отчёт обновится. Если файла нет,
он будет сгенерирован автоматически.

## Roadmap

Идеи, **не реализованные** в текущей версии (намеренно отложены):

- **Гибридный поиск**: BM25/лексический + вектор, с ре-ранкингом.
- **Инкрементальная индексация**: перестройка только изменённых документов
  вместо полного пересбора.
- **Auto-tuning параметров chunking**: автоподбор `max_tokens` /
  `overlap_tokens` / порогов по метрикам eval.
- Больше типов эталонов (заголовочные + человеческие в одном пуле) для
  честной оценки `heading` vs `faq`.

## `gwclub serve` — HTTP-sidecar для поиска

Отдельный процесс, отдающий результаты поиска по уже построенному
FAISS-индексу через локальный HTTP. Сделан для внешних потребителей, которым
не нужен Python-интерфейс (например, RAG-режим веб-приложения «Штурман»):
один `POST /search` возвращает top-k чанков. Реализация на чистом stdlib
(`http.server`), новых зависимостей нет; существующее CLI-поведение
индексера не меняется.

### Потребители

RAG-потребителей два — оба продукта называются «Штурман» (исторически:
Telegram-бот выделен из веб-приложения в отдельный репозиторий). Оба ходят
через `POST /search`, но в разные экземпляры сервиса:

| Потребитель | Репозиторий | Экземпляр | Endpoint |
|---|---|---|---|
| Веб-приложение | `Projects/ai-challenge-9` | контейнер `indexer` (его compose) | `http://indexer:8000/search` — внутренняя compose-сеть |
| Telegram-бот | `Projects/shturman-bot` | хостовый sidecar `gwclub serve` | `http://host.docker.internal:18700/search` (`RAG_SEARCH_URL`) |

Разница экземпляров — скорость реранка: контейнер работает на CPU
(медиана реранка 20 кандидатов ≈1.9 с), хостовый sidecar — на MPS
(≈1.0 с), поэтому бот в v1-архитектуре ходит на хостовый процесс ради
скорости ответа. Индекс у обоих один — `data/index` (в контейнер
монтируется read-only).

### Запуск

Индекс для выбранной стратегии обязан быть построен (`gwclub index`).
Сервер запускается **из корня репозитория**: `index_dir` в конфиге
относительный (`data/index`) и автоматически не резолвится.

```bash
cd gw-club-indexer && uv run gwclub serve --port 18700
```

Старт fail-fast: отсутствующий или рассинхронный индекс (модель/размерность
эмбеддера не совпадает с метаданными `index_meta`) оборачивается в
`error: ...` в stderr и ненулевой код выхода (2 для mismatch, 1 для
отсутствующих артефактов). Здоровый сервер после старта по запросам не
отдаёт 500.

### Флаги

| Флаг | Дефолт | Смысл |
|---|---|---|
| `--config` | (отсутствует) | Путь к override-файлу `config.toml`; без флага работают дефолты из кода. |
| `--strategy` | `null` → `cfg.default_search_strategy` (`structure`) | Стратегия индекса: `fixed` или `structure`. |
| `--host` | `127.0.0.1` | Адрес привязки сервера. |
| `--port` | `18700` | Порт привязки. |
| `-k`, `--k` | `5` | top-k по умолчанию для запросов без поля `k` в теле. |

### Контракт `POST /search`

Тело запроса: JSON-объект `{"query": "<текст>", "k": <int, опционально>}`.
`k` из тела перекрывает `--k`; значение клампится в `[1, 50]`,
нецелочисленное (bool, float, строка) считается отсутствующим.

| Код | Когда | Тело ответа |
|---|---|---|
| `200` | Успех | JSON-массив `[{chunk_id, score, source, title, section, content}]` |
| `400` | Пустой/пробельный/не-строковый `query`; пустое или не-объектное тело | `{"error": "Пустой запрос"}` |
| `404` | Любой другой путь; любой метод, кроме POST | `{"error": "Not Found"}` |
| `500` | Сбой индекса при выполнении запроса | `{"error": "<msg>"}` |

**Контракт:** поле `content` несёт **полный текст чанка** (а не snippet в
200 символов, как в CLI `gwclub search`). `score` округлён до 4 знаков.
Именно здесь потребитель RAG получает полный текст для промпта; в ответы и
журналы обычно уходят только метаданные.

Примеры:

```bash
# Успех: top-2 по структурированному индексу.
curl -s -X POST http://127.0.0.1:18700/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"прошивка","k":2}'

# Пустой запрос → 400.
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:18700/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"  "}'
```

### Прогрев и потоки

- **Preload один раз при старте**: `build_server` загружает config,
  эмбеддер, FAISS-индекс и карту строк (SQLite row_map) до первого запроса
  и проверяет согласованность метаданных.
- **Warm-up**: один `embed_query("warmup")` до `serve_forever` прогоняет
  модель, чтобы первый реальный запрос не ждал загрузки весов. Строка
  `gwclub serve: стратегия <s>, N чанков, модель прогрета, порт P` пишется
  в stdout с `flush=True` (видна и в фоновом nohup-логе).
- **Потоки**: сервер `ThreadingHTTPServer` (поток на запрос), но
  `SentenceTransformer.encode` не потокобезопасен: вокруг embed+search
  держится глобальный `threading.Lock`, поэтому запросы сериализуются.

### Этап 2 (stage-2): реранк, порог, пул кандидатов

Пост-обработка после векторного поиска живёт в одном месте
(`search_pipeline` в serve.py): `search(k_before)` → (если `rerank`)
реранк под тем же `lock`'ом + сортировка по убыванию → порог
`score >= threshold` → top-k. Запрос без новых параметров байт-в-байт
не отличается от v1 (byte-identity подтверждён: sha256 тела совпадает
с эталоном фазы 1).

Новые опциональные поля тела `POST /search` (все несут v1-поведение по
отсутствию):

| Параметр | Дефолт | Смысл |
|---|---|---|
| `k_before` | `k` | Размер пула кандидатов до пост-обработки. Клампится в `[1, 50]` как `k`; если `k_before < k` — автоматически поднимается до `k` (НЕ 400); нецелочисленное (bool, float, строка) — 400. |
| `threshold` | `null` (без фильтра) | Порог отсечения по ФИНАЛЬНОЙ шкале score: `rerank=false` → косинус `[-1, 1]`; `rerank=true` → сигмоид `[0, 1]`. bool/не-число или значение вне диапазона активной шкалы → 400 по-русски с указанием диапазона. |
| `rerank` | `false` | Переранжировать кандидатов cross-encoder'ом. `true` без флага `--rerank-model` → 400 «Реранкер не настроен: запустите serve с --rerank-model». |

`score` в ответе — финальная шкала (косинус при `rerank=false`, сигмоид
при `rerank=true`), как и в v1, округлённая до 4 знаков. Шкалы не
смешиваются: порог всегда сравнивается с той шкалой, на которой ответ.
Сбой модели при выполнении реранка → 500 по-русски.

Пример:

```bash
# top-3: пул 20 кандидатов, реранк, отсечение по сигмоиде 0.5.
curl -s -X POST http://127.0.0.1:18700/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"прошивка","k":3,"k_before":20,"rerank":true,"threshold":0.5}'
```

#### Флаг `--rerank-model`

| Флаг | Дефолт | Смысл |
|---|---|---|
| `--rerank-model` | `cfg.search.rerank_model` (обычно unset) | id модели CrossEncoder (например `BAAI/bge-reranker-v2-m3`); без флага `rerank=true` невозможен. |

Веса модели не лежат в репо: ~2.2 GB, скачиваются с Hugging Face в кэш
(`~/.cache/huggingface`) при первом serve с флагом. На старте serve
реранкер прогревается одним score-вызовом (как warm-up эмбеддера),
поэтому первый реальный запрос не ждёт загрузки; сбой загрузки —
конфигурационная ошибка: сервер не стартует (код выхода 1,
`error: ...` в stderr).

Реранкер идёт на MPS («auto»). **Не переводите serve-процесс на
CPU-модели**: если faiss импортирован раньше загрузки torch-модели в одном
процессе, процесс молча погибает на первом score-вызове — без traceback
и сегфолт-баннера (проверено 11.10.2026; обратный порядок импортов
выживает, для CPU-пути нужен ленивый импорт faiss). Риск GPU-конкуренции
с LM Studio (Metal Timeout 10.10.2026, 23:21) смягчается малым `k_before`
и отключённым JIT у LM Studio.

#### Числа из проба (reports/stage2-probe.md)

- Латентность реранка 20 кандидатов (медиана): CPU (fp32) ≈1.9 с,
  MPS ≈1.0 с; оба < 5 с, риск по таймаутам не зафиксирован.
- Холодная загрузка модели из кэша: MPS ≈4.8 с (первое скачивание
  ~2.2 GB заняло ~150 с).
- Косинусы e5 в этом корпусе сжаты в 0.84–0.95 (top-20): абсолютный
  порог по косинусу — не фильтр релевантности, только защитный
  хвост-кат.
- Рекомендуемые дефолты: `k_before = min(4*k, 50)` (для `k=5` — 20);
  при `rerank=true` порог `threshold = 0.5` (релевантные чанки ~0.96,
  шум ~0.001, тематически-близкие 0.6–0.99).

### Docker

Сервис поднимается не сам, а compose'ом веб-приложения
(`Projects/ai-challenge-9/docker-compose.yml`, сервис `indexer`; build-context
корня этого репозитория, `dockerfile: Dockerfile`). Telegram-бот контейнер
не поднимает — он работает с хостовым sidecar (см. «Потребители»).
Команда запуска и все артефакты задаёт compose:

```bash
uv run gwclub serve --host 0.0.0.0 --port 8000 --rerank-model BAAI/bge-reranker-v2-m3
```

- `--host 0.0.0.0` обязателен: дефолт `serve.py` равен `127.0.0.1`
  (см. «Флаги»), иначе контейнер молча недоступен. Порт внутри контейнера
  равен `8000` (`EXPOSE 8000` в Dockerfile).
- Порт наружу опубликован только как `127.0.0.1:18701` (отладка с хоста,
например `curl -s -X POST http://127.0.0.1:18701/search -H 'Content-Type:
application/json' -d '{"query":"прошивка","k":3}'`). Веб-приложение
«Штурман» (aiweb, репозиторий `ai-challenge-9`) ходит по внутренней
compose-сети на `http://indexer:8000/search` (секция `rag` его конфига);
Telegram-бот (`Projects/shturman-bot`) использует хостовый sidecar
`:18700` (см. «Потребители»).
- `restart: unless-stopped`; healthcheck в compose не дублируется и берётся
  из образа (TCP one-liner на `127.0.0.1:8000`, `start_period 600s`). При
  первом старте контейнер докачивает веса моделей в именованный том
  `hf-cache:/home/indexer/.cache/huggingface` (~2.7 ГБ: bge-reranker ~2.2 +
  e5 ~0.5), до healthy может пройти 10-15 минут; докачка resume-able,
  повторный старт идёт с тёплого тома.
- Второй том `data/index:/app/data/index:ro`: готовый индекс с хоста,
  read-only. Он обязан быть построен до старта (`gwclub index`). После
  ребилда индекса на хосте контейнеру нужен `docker compose restart indexer`:
  новые файлы ro-монтирования не подхватываются на лету.
- RAM хоста нужна не меньше 8 ГБ: в контейнере живут эмбеддер E5 и
  CPU-реранкер bge-reranker-v2-m3. В контейнере нет MPS: медиана реранка 20 кандидатов
  ≈1.9 с (CPU, fp32) против ≈1.0 с на MPS хоста (см. «Числа из проба»);
  бюджет `timeoutMs` в секции `rag` на это и рассчитан.
- Пользователь образа: непривилегированный `indexer`, HF-кэш лежит в
  `/home/indexer/.cache/huggingface` (том `hf-cache`). Если смените
  пользователя в Dockerfile, сбросьте том: `docker volume rm hf-cache`,
  иначе HF-кэш, созданный прежним uid, будет недоступен новому.
- Место на диске: образ ~6.6 ГБ + том `hf-cache` ~2.7 ГБ.
