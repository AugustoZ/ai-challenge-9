# Пайплайн-сценарии

Каталог сценариев для `POST /api/pipeline/run` (движок — `src/main/kotlin/com/example/aiweb/pipeline/`).
Каждый `.json` файл здесь — один именованный сценарий; имя файла = имя сценария в запросе (`"scenario": "faq-24h"`).

## Формат сценария

Сценарий сериализуется в `com.example.aiweb.pipeline.PipelineScenario`:

```json
{
  "name": "faq-24h",
  "description": "Одно-два предложения о том, что делает сценарий (опционально, но рекомендуется).",
  "steps": [
    { "id": "s1", "tool": "mcp__tg__read_recent", "args": { "hours": 24, "max_messages": 500 } },
    { "id": "s2", "tool": "summarize", "args": { "text": "…", "instruction": "…" }, "optional": true }
  ]
}
```

Поля:

| Поле | Обязательное | Описание |
|---|---|---|
| `name` | да | Имя сценария (должно совпадать с базовым именем файла). |
| `description` | нет | Короткое описание (идёт в `/api/pipeline/status`-отчёты и документацию). |
| `steps[]` | да | Шаги исполняются **линейно, по порядку**, без ветвлений и ретраев. |
| `steps[].id` | да | Уникальный id шага (используется в плейсхолдерах). |
| `steps[].tool` | да | Имя инструмента из реестра: встроенный (`summarize`, `saveToFile`, …) или MCP-тул `mcp__<сервер>__<тул>`. |
| `steps[].args` | нет | JSON-объект аргументов инструмента (по его `parametersJsonSchema`). |
| `steps[].optional` | нет | `true` — упавший шаг не останавливает пайплайн (помечается `failed`, дальше идут остальные). |

## Плейсхолдеры `${steps.<id>.result}`

Ссылка на результат уже выполненного шага:

- строка **ровно** равная плейсхолдеру → **структурная подстановка**: если результат шага — валидный JSON, он вставляется как JSON-значение (объект/массив), иначе как строка;
- плейсхолдер **внутри** большей строки → обычная строковая интерполяция;
- ссылка на неизвестный или ещё не выполненный шаг → провал пайплайна.

Результаты шагов капаются 20 000 символов.

### Как добавить свой сценарий

1. Положите файл `config/pipelines/<имя>.json` в этот каталог (формат выше).
2. Проверьте имена тулов и имена аргументов: встроенные — в `src/main/kotlin/com/example/aiweb/tools/`, MCP-тулы — в `mcp-servers/*_server.py` (сигнатуры функций).
3. Запустите: `POST /api/pipeline/run` с `{"scenario": "<имя>"}` (202 → статус через `GET /api/pipeline/status`).

## Как назвать серверы в config.json

Имя MCP-тула, которое ожидает сценарий — `mcp__<имя сервера в config.json>__<тул>`.
Сценарий `faq-24h` ссылается на `mcp__tg__read_recent`, `mcp__tg__summary`, `mcp__wiki__append_faq_page`,
то есть в `config.json` (блок `mcp`) серверы должны называться ровно **`tg`** и **`wiki`**:

```json
"mcp": [
  { "name": "tg",   "command": "…/mcp-servers/.venv/bin/python", "args": ["…/mcp-servers/tg_server.py"],   "enabled": true },
  { "name": "wiki", "command": "…/mcp-servers/.venv/bin/python", "args": ["…/mcp-servers/wiki_server.py"], "enabled": true }
]
```

Внутреннее (рекламируемое серверами) имя `shturman-tg` / `shturman-wiki` для сценария **не важно** — префикс строится только из имени в `config.json`.
Если ваш сервер называется иначе — подставьте свой префикс в `tool` соответствующих шагов.

## Отклонения сценария faq-24h от исходной идеи

- **Имя файла без `<timestamp>`**: инструмент `saveToFile` пишет файл по имени как есть, подстановку `<timestamp>` не умеет (это свойство движка, а не инструмента). Поэтому `s4` сохраняет в **статичное** имя `faq-24h.md` — при каждом прогоне файл **перезаписывается** (это поведение saveToFile: существующий файл перезаписывается целиком).
- Остальные аргументы шагов сверены с реальными сигнатурами тулов (задачи 4/7/8) и совпадают с ними.
